# 0028. Docker Engine в своём WSL2-дистрибутиве, запуск без входа пользователя

**Статус:** принято

## Контекст

Задача #6 (AR-5): после перезагрузки хоста стек поднимается сам, без ручных
действий, и `/health` отвечает. Хост — ПК с Windows 11, позже переезд на
другой ПК с Windows 11, поэтому настройка должна воспроизводиться сценарием
из репозитория.

У всех сервисов compose стоит `restart: unless-stopped`, и этого достаточно,
когда работает демон Docker. Но Docker Desktop стартует только в сессии
вошедшего пользователя. Без входа демона нет, а значит, нет и стека.

## Решение

Стек переезжает с Docker Desktop на Docker Engine в отдельном
WSL2-дистрибутиве `domovoy-engine` (Ubuntu 24.04). Настройку делает
`deploy/windows/engine-setup.ps1 -Install`, проверку — `-Check`.

Цепочка после включения питания:

1. BIOS включает ПК после пропадания питания. Это предусловие, сценарий его
   не проверяет. BitLocker — без PIN до загрузки.
2. Windows загружается до экрана входа, в сессию никто не входит.
3. Задача Планировщика `domovoy-engine` срабатывает при запуске системы. Она
   идёт от учётной записи владельца с типом входа **S4U**: пароль не хранится.
   Задача запускает держалку `wsl.exe -d domovoy-engine --exec sleep infinity`.
4. systemd дистрибутива (`/etc/wsl.conf`, `[boot] systemd=true`) поднимает
   `containerd` и `docker`, а dockerd — контейнеры по политике `restart`.

Опыт владельца 2026-10-12 (журнал `docs/tasks/6.md`, «Проверено») показал на
пустом дистрибутиве: задача S4U подняла его через 20 с после загрузки, до
входа. Внутри systemd был `running`, порт из ЛВС отвечал.

Отдельные решения внутри способа:

- **Принципал — учётная запись владельца, а не SYSTEM.** Дистрибутив WSL
  регистрируется на пользователя, под SYSTEM его не видно.
- **Держалка `sleep infinity`.** Экземпляр WSL живёт, пока жив хоть один
  процесс `wsl.exe`. Без держалки дистрибутив остановится после тайм-аута
  простоя, а вместе с ним остановится и движок. У задачи
  `ExecutionTimeLimit 0`, потому что предел по умолчанию в 72 ч убил бы
  держалку на третьи сутки. Батарея не мешает ни старту, ни работе задачи:
  UPS по USB Windows видит батареей. При сбое задача перезапускается.
- **Сеть `networkingMode=mirrored`** в `%USERPROFILE%\.wslconfig`. Порты
  контейнеров видны на адресе хоста в ЛВС. Переписывать проброс при каждой
  загрузке не нужно. Файл глобален для всех дистрибутивов пользователя.
  Поэтому прежний файл сохраняется копией, а другое значение
  `networkingMode` — это отказ сценария, а не перезапись. Так же отказ —
  `firewall=false`: правило ниже сужает доступ, только пока firewall Hyper-V
  для VM WSL включён и по умолчанию блокирует входящие; `-Check` сверяет
  это по действующей настройке (`Get-NetFirewallHyperVVMSetting`).
- **Правило Hyper-V firewall** открывает входящие TCP на `API_HTTP_PORT` и
  `HA_HTTP_PORT`. Источники — только локальная подсеть и адреса петли хоста
  (`127.0.0.1`; `::1` правило Hyper-V не принимает —
  «Параметр задан неверно»). Поэтому с самого хоста стек открывается по
  `127.0.0.1`, а не `localhost`: Windows пробует `localhost` сначала как
  `::1`, и запрос висит до тайм-аута (живой прогон 2026-10-13: на
  `127.0.0.1` — 200, на `localhost` и `[::1]` — тайм-аут). `-Check` и замер
  стучатся на `127.0.0.1`. Правило действует **только в
  профиле сети Private**: хост — ноутбук, и без профиля `LocalSubnet`
  чужой сети (общественный Wi-Fi) видел бы порты HA и API. Сеть хоста дома
  должна быть частной — предусловие README. Наружу HA по-прежнему не
  выставляется (NFR-SEC-2): проброса на роутере нет.
- **MSS по PMTU для трафика контейнеров** — юнит systemd
  `domovoy-mss-clamp.service` (oneshot, `RemainAfterExit=yes`, до
  `docker.service`) ставит при каждом старте дистрибутива правило iptables
  `-t mangle FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS
  --clamp-mss-to-pmtu` (`-C` перед `-A` — без дублей). Причина — живой
  прогон: у хоста VPN с MTU 1420, HTTPS из сети моста (MTU 1500) висел —
  `dotnet restore` при сборке api не достучался до nuget, — а с `--network
  host` проходил. `-Check` требует у юнита и `is-enabled enabled`, и
  `is-active active`.
- **docker и compose выполняются внутри дистрибутива.** Клон там виден как
  `/mnt/<диск>/…`, и bind mount `./config` движок находит. Из Git Bash
  команды идут через обёртку `deploy/windows/docker-wsl.sh`:
  `wsl.exe --cd <каталог> --exec docker …`.
- **Сценарии бэкапа (#8) идут внутри дистрибутива, а не через обёртку.**
  Задача `domovoy-backup` под S4U запускает
  `wsl.exe -d domovoy-engine --cd <клон> --exec bash ops/backup/backup.sh`.
  Для неё docker — сам движок: без функции из `~/.bashrc`, которую
  неинтерактивный bash не читает, и без двойного interop для бинарных потоков
  дампа. `BACKUP_DIR` вида `D:/…` переводит `wslpath`.
- **Порты не зашиты.** Они берутся из `API_HTTP_PORT` и `HA_HTTP_PORT` в
  `.env`, без них — из значений по умолчанию в `docker-compose.yml`.
- **Софт хоста.** Добавляются дистрибутив Ubuntu 24.04 (официальный образ
  `cloud-images.ubuntu.com`; SHA256 сверяется с `SHA256SUMS` того же
  сервера — проверка целостности загрузки, не подлинности: подпись
  `SHA256SUMS` не проверяется, gpg ради неё не ставится) и пакеты
  `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`,
  `docker-compose-plugin`, `git` из официального репозитория apt Docker, а
  также свой юнит systemd `domovoy-mss-clamp.service` (iptables приходит с
  `docker-ce`, отдельных пакетов юнит не ставит). В сборку и зависимости
  проекта ничего из этого не входит.
- **Замер** — задача `domovoy-measure-boot` при запуске системы
  (`deploy/windows/measure-boot.ps1`). Она пишет строку от старта ОС
  (Kernel-General 12) до первого ответа 200 формы стека в
  `%LOCALAPPDATA%\domovoy-engine\measure-boot.log`. Принципал тот же, что у
  держалки: пользователь, S4U, обычные права. Задача исполняет файл из
  клона, а клон пользователь может менять, поэтому под SYSTEM это было бы
  повышением прав. Нужное замеру читается и без администратора.

Docker Desktop не удаляется до приёмки — это путь отката. Его тома остаются
нетронутыми: стек на нём останавливается через `stop`, а не через
`down -v`.
Откат — `engine-setup.ps1 -Uninstall`: снимает задачи автозапуска, чтобы
после перезагрузки рядом с Docker Desktop не поднялся второй стек, и
оставляет дистрибутив с томами.

## Отвергнутые варианты

- **Автовход Windows (Sysinternals Autologon), автозапуск Docker Desktop и
  блокировка экрана.** Отверг владелец: пароль учётной записи перестаёт
  защищать загрузку. Пароль автовхода — секрет LSA, и администратор хоста
  может его извлечь.
- **Тип входа Password у задачи.** Планировщик хранит пароль учётной записи —
  то же свойство, за которое отвергнут автовход. Сценарии такой тип не
  собирают.
- **Задача под SYSTEM, запускающая `wsl.exe`.** Дистрибутив зарегистрирован
  на пользователя и под SYSTEM не виден.
- **Сеть NAT и `netsh interface portproxy` на адрес ВМ.** Адрес ВМ меняется
  на каждой загрузке. Проброс пришлось бы переписывать при старте, а это
  лишнее звено в цепочке автозапуска.
- **Docker CLI Windows ходит в dockerd по TCP (2375/2376) или через
  ssh-контекст.** Bind mount `./config` CLI Windows передаёт путём Windows,
  а Linux-движок такой каталог не находит: переводит такие пути только
  Docker Desktop. Кроме того, 2375 без TLS даёт root в движке любому
  локальному процессу.
- **Собственный перенос томов** вместо сценариев #8. Это два способа
  перенести одни данные, и они разъедутся.
- **Сценарии в `scripts/`.** Там обвязка конвейера агента, а это
  эксплуатация продукта, поэтому сценарии лежат в `deploy/windows/`.

## Следствия

- Команды `docker` из README и `.claude/CLAUDE.md` на этом хосте идут через
  функцию `docker()` в `~/.bashrc`, которая вызывает обёртку. Абсолютные пути
  Windows в аргументах обёртка не переводит. `-it` зависит от TTY Git Bash.
- `.wslconfig` (mirrored) действует на все дистрибутивы пользователя.
  Применяется он после `wsl --shutdown`, который выполняет владелец в окне
  переезда.
- Сразу после загрузки dockerd может ещё подниматься. Пропущенный ночной
  бэкап, который Планировщик запускает при первой возможности, в этом окне
  может отказать. Отказ пишется строкой в `backup.log`, а следующий запуск
  идёт в срок.
- Доступ из ЛВС `-Check` с хоста не проверяет: в mirrored хост не достаёт
  до слушателя дистрибутива по своему адресу в ЛВС (`hostAddressLoopback`
  по умолчанию выключен и не включается). Его проверяет телефон в домашней
  сети.
- `localhost` на хосте с движком не отвечает (Windows пробует сначала
  `::1`, а `::1` правило Hyper-V не принимает) — проверено живым прогоном,
  рабочий адрес с хоста — `127.0.0.1`.
- Без входа пользователя не проверено одно звено, его проверяет живой прогон
  владельца: монтируется ли в `/mnt/<диск>` работающего дистрибутива
  носитель, подключённый после его старта.
- Перезагрузка или выключение Windows не останавливает контейнеры
  аккуратно: ВМ WSL гасится, как при пропаже питания (установлено на живом
  хосте 2026-10-13). PostgreSQL при следующем старте пишет «database system
  was not properly shut down; automatic recovery in progress» и
  восстанавливается по WAL за доли секунды. Данные БД не теряются: WAL
  пишется с fsync. Теряется хвост логов контейнеров (json-file, без fsync) —
  последние минуты до выключения. На нём же рвётся чтение `docker logs`
  целиком, поэтому логи читаются с `--tail`. Аккуратная остановка при
  выключении хоста не делается: на Windows Home нет штатного сценария
  завершения работы без групповой политики, а для БД это повтор пропажи
  питания, которую она и так переживает. По этой же причине по логам api не
  удалось восстановить причину временного ответа unhealthy после холодной
  загрузки.

## Дополнения

### 2026-10-13, #147: путь через Docker Desktop снят

Переезд на движок выполнен, владелец удаляет Docker Desktop, и на новом ПК
будет только движок. Поэтому абзац «Docker Desktop не удаляется до
приёмки — это путь отката» больше не действует, а из сценариев снято всё,
что держало этот путь:

- режим `engine-setup.ps1 -Migrate` (разовый переезд, он уже выполнен);
- в `-Uninstall` — возврат автозапуска Docker Desktop и перевод расписания
  бэкапа под Desktop. Теперь `-Uninstall` снимает движок — задачи,
  расписание бэкапа (без движка оно ночью будило бы WSL), правило firewall,
  `.wslconfig` — и никуда не откатывает; дистрибутив с томами остаётся;
- в `-Check` — звенья про процессы и автозапуск Docker Desktop;
- в `ops/backup/install-schedule.ps1` — ветка `-LogonType Interactive` с
  поиском Git Bash: задача бэкапа всегда S4U, внутри дистрибутива.

Новый ПК — один путь: `engine-setup.ps1 -Install`, затем `restore.sh
--project … --from …` из последнего бэкапа внутри дистрибутива (README,
«Автозапуск после перезагрузки», «Новый ПК»).

### 2026-10-13, #147: логи контейнеров — журнал systemd на диске

Следствие выше — хвост логов json-file теряется при выключении хоста, и на
оборванном файле рвётся `docker logs`, — помешало разобрать ответ unhealthy
после холодной загрузки. Поэтому `provision-engine.sh` переводит движок на
драйвер логов `journald` (`/etc/docker/daemon.json`; чужой файл не
переписывается — отказ) и держит журнал systemd на диске со сбросом раз в
10 с (drop-in `/etc/systemd/journald.conf.d/domovoy-journal.conf`:
`Storage=persistent`, `SyncIntervalSec=10s`). После жёсткого отключения
теряются последние секунды до сброса, а не минуты. `-Check` проверяет
действующую настройку журнала, драйвер движка и драйвер у каждого
контейнера проекта. Драйвер — настройка движка, а не `docker-compose.yml`:
тот же compose работает на машинах разработки и в CI, где журнала нет.
Читаются логи `docker logs` (через обёртку) и `journalctl
CONTAINER_NAME=<имя>` внутри дистрибутива, в том числе за прошлый запуск
(README, «Логи и хронология загрузки»). Кэш записи виртуального диска на
стороне Windows настройкой внутри ВМ не управляется — переживание
отключения проверяется живым снятием питания.
