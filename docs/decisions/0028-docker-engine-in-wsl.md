# 0028. Docker Engine в своём WSL2-дистрибутиве, запуск без входа пользователя

**Статус:** принято

## Контекст

Задача #6 (AR-5): после перезагрузки хоста стек поднимается сам, без ручных
действий, и `/health` отвечает. Хост — ПК с Windows 11, позже переезд на
другой ПК с Windows 11, поэтому настройка должна воспроизводиться сценарием
из репозитория.

У всех сервисов compose стоит `restart: unless-stopped`, и этого достаточно,
когда работает демон Docker. Но Docker Desktop стартует только в сессии
вошедшего пользователя. Без входа демона нет, а значит, нет и стека.

## Решение

Стек переезжает с Docker Desktop на Docker Engine в отдельном
WSL2-дистрибутиве `domovoy-engine` (Ubuntu 24.04). Настройку делает
`deploy/windows/engine-setup.ps1 -Install`, проверку — `-Check`.

Цепочка после включения питания:

1. BIOS включает ПК после пропадания питания. Это предусловие, сценарий его
   не проверяет. BitLocker — без PIN до загрузки.
2. Windows загружается до экрана входа, в сессию никто не входит.
3. Задача Планировщика `domovoy-engine` срабатывает при запуске системы. Она
   идёт от учётной записи владельца с типом входа **S4U**: пароль не хранится.
   Задача запускает держалку `wsl.exe -d domovoy-engine --exec sleep infinity`.
4. systemd дистрибутива (`/etc/wsl.conf`, `[boot] systemd=true`) поднимает
   `containerd` и `docker`, а dockerd — контейнеры по политике `restart`.

Опыт владельца 2026-10-12 (журнал `docs/tasks/6.md`, «Проверено») показал на
пустом дистрибутиве: задача S4U подняла его через 20 с после загрузки, до
входа. Внутри systemd был `running`, порт из ЛВС отвечал.

Отдельные решения внутри способа:

- **Принципал — учётная запись владельца, а не SYSTEM.** Дистрибутив WSL
  регистрируется на пользователя, под SYSTEM его не видно.
- **Держалка `sleep infinity`.** Экземпляр WSL живёт, пока жив хоть один
  процесс `wsl.exe`. Без держалки дистрибутив остановится после тайм-аута
  простоя, а вместе с ним остановится и движок. У задачи
  `ExecutionTimeLimit 0`, потому что предел по умолчанию в 72 ч убил бы
  держалку на третьи сутки. Батарея не мешает ни старту, ни работе задачи:
  UPS по USB Windows видит батареей. При сбое задача перезапускается.
- **Сеть `networkingMode=mirrored`** в `%USERPROFILE%\.wslconfig`. Порты
  контейнеров видны на адресе хоста в ЛВС. Переписывать проброс при каждой
  загрузке не нужно. Файл глобален для всех дистрибутивов пользователя.
  Поэтому прежний файл сохраняется копией, а другое значение
  `networkingMode` — это отказ сценария, а не перезапись.
- **Правило Hyper-V firewall** открывает входящие TCP на `API_HTTP_PORT` и
  `HA_HTTP_PORT`. Источники — только локальная подсеть и адреса петли хоста
  (`127.0.0.1`, `::1`). В опыте при правиле только на `LocalSubnet` запрос с
  `localhost` Windows уходил в тайм-аут. Наружу HA по-прежнему не выставляется
  (NFR-SEC-2): проброса на роутере нет.
- **docker и compose выполняются внутри дистрибутива.** Клон там виден как
  `/mnt/<диск>/…`, и bind mount `./config` движок находит. Из Git Bash
  команды идут через обёртку `deploy/windows/docker-wsl.sh`:
  `wsl.exe --cd <каталог> --exec docker …`.
- **Сценарии бэкапа (#8) идут внутри дистрибутива, а не через обёртку.**
  Задача `domovoy-backup` под S4U запускает
  `wsl.exe -d domovoy-engine --cd <клон> --exec bash ops/backup/backup.sh`.
  Для неё docker — сам движок: без функции из `~/.bashrc`, которую
  неинтерактивный bash не читает, и без двойного interop для бинарных потоков
  дампа. `BACKUP_DIR` вида `D:/…` переводит `wslpath`.
- **Порты не зашиты.** Они берутся из `API_HTTP_PORT` и `HA_HTTP_PORT` в
  `.env`, без них — из значений по умолчанию в `docker-compose.yml`.
- **Софт хоста.** Добавляются дистрибутив Ubuntu 24.04 (официальный образ
  `cloud-images.ubuntu.com`, SHA256 сверяется с `SHA256SUMS`) и пакеты
  `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`,
  `docker-compose-plugin`, `git` из официального репозитория apt Docker. В
  сборку и зависимости проекта ничего из этого не входит.
- **Замер** — задача `domovoy-measure-boot` при запуске системы
  (`deploy/windows/measure-boot.ps1`). Она пишет строку от старта ОС
  (Kernel-General 12) до первого ответа 200 формы стека в
  `%LOCALAPPDATA%\domovoy-engine\measure-boot.log`. Принципал тот же, что у
  держалки: пользователь, S4U, обычные права. Задача исполняет файл из
  клона, а клон пользователь может менять, поэтому под SYSTEM это было бы
  повышением прав. Нужное замеру читается и без администратора.

Docker Desktop не удаляется до приёмки — это путь отката. Его тома остаются
нетронутыми: стек на нём останавливается через `stop`, а не через
`down -v`.

## Отвергнутые варианты

- **Автовход Windows (Sysinternals Autologon), автозапуск Docker Desktop и
  блокировка экрана.** Отверг владелец: пароль учётной записи перестаёт
  защищать загрузку. Пароль автовхода — секрет LSA, и администратор хоста
  может его извлечь.
- **Тип входа Password у задачи.** Планировщик хранит пароль учётной записи —
  то же свойство, за которое отвергнут автовход. Сценарии такой тип не
  собирают.
- **Задача под SYSTEM, запускающая `wsl.exe`.** Дистрибутив зарегистрирован
  на пользователя и под SYSTEM не виден.
- **Сеть NAT и `netsh interface portproxy` на адрес ВМ.** Адрес ВМ меняется
  на каждой загрузке. Проброс пришлось бы переписывать при старте, а это
  лишнее звено в цепочке автозапуска.
- **Docker CLI Windows ходит в dockerd по TCP (2375/2376) или через
  ssh-контекст.** Bind mount `./config` CLI Windows передаёт путём Windows,
  а Linux-движок такой каталог не находит: переводит такие пути только
  Docker Desktop. Кроме того, 2375 без TLS даёт root в движке любому
  локальному процессу.
- **Собственный перенос томов** вместо сценариев #8. Это два способа
  перенести одни данные, и они разъедутся.
- **Сценарии в `scripts/`.** Там обвязка конвейера агента, а это
  эксплуатация продукта, поэтому сценарии лежат в `deploy/windows/`.

## Следствия

- Команды `docker` из README и `.claude/CLAUDE.md` на этом хосте идут через
  функцию `docker()` в `~/.bashrc`, которая вызывает обёртку. Абсолютные пути
  Windows в аргументах обёртка не переводит. `-it` зависит от TTY Git Bash.
- `.wslconfig` (mirrored) действует на все дистрибутивы пользователя.
  Применяется он после `wsl --shutdown`, который выполняет владелец в окне
  переезда.
- Сразу после загрузки dockerd может ещё подниматься. Пропущенный ночной
  бэкап, который Планировщик запускает при первой возможности, в этом окне
  может отказать. Отказ пишется строкой в `backup.log`, а следующий запуск
  идёт в срок.
- Без входа пользователя не проверены два звена, их проверяет живой прогон
  владельца:
  - отвечает ли `localhost` с правилом, дополненным адресами петли;
  - монтируется ли в `/mnt/<диск>` работающего дистрибутива носитель,
    подключённый после его старта.
