# 0035. Разделы общего лимита частоты

**Статус:** принято
**Дополняет:** [0033](0033-admin-endpoints-shared-secret.md) — раздел лимита
`/auth/device` остаётся прежним

## Контекст

NFR-SEC-3 требует ограничения частоты запросов. До #17 лимит был только у
обмена кода привязки (запись 0033), остальные эндпоинты, включая анонимный
`/health`, не ограничивались ничем. Публичный домен сканируется постоянно, а
`/health` на каждом вызове опрашивает компоненты — базу, Home Assistant и
провайдера LLM. Задача требует лимита на всех эндпоинтах и отдельного, более
жёсткого — на `/chat` и `/voice`.

Как делить общий лимит на разделы, ТЗ не говорит. Выбор неочевиден:
раздел по адресу источника за туннелем вырождается, а по заголовку туннеля
обходится подделкой (0033, «Компромисс общего раздела лимитера»).

## Решение

- **Механизм** — встроенный `Microsoft.AspNetCore.RateLimiting`, без новых
  пакетов: глобальный лимитер на каждом маршруте плюс политики `llm` и
  `pairing`. Окно всех пределов — фиксированная минута, очереди нет.
  Пределы — `RateLimit:RequestsPerMinute` (120) и
  `RateLimit:LlmRequestsPerMinute` (10); предел привязки —
  `Auth:PairingAttemptsPerMinute`, как в 0033.
- **Раздел общего лимита — из установленной личности и конечной точки**, ни
  одного значения из заголовков запроса:
  - `device:<id>` — устройство по действующему токену;
  - `admin` — администратор по общему секрету;
  - `local` — анонимный запрос с петли (`127.0.0.1`, `::1`, IPv4-mapped
    приводится к IPv4): healthcheck контейнера и проверка тела `/health` при
    обновлении;
  - `anonymous:<имя конечной точки>` — остальные анонимные запросы, свой
    раздел у каждой анонимной конечной точки (`health-liveness`,
    `auth-device`).

  Число разделов ограничено числом устройств и конечных точек: ключа,
  который запрос выбирает сам, нет, и чужие запросы не плодят лимитеры.
- **Лимитер после авторизации.** Схемы по умолчанию нет, и личность
  устройства появляется в запросе только в `UseAuthorization`. Поэтому
  `UseRateLimiter` стоит после неё.
- **`/chat` и `/voice` — один раздел на дом.** Бюджет токенов один
  (NFR-COST-2): предел на устройство умножался бы на число устройств и
  бюджет не ограничивал. `LlmRequestsPerMinute` строго меньше
  `RequestsPerMinute`, иначе отказ старта: равный предел ничего не добавлял
  бы к общему.
- **Отказ** — `429` `rate_limited` в едином формате с `Retry-After` от 1 до
  60 секунд; Warning в лог с маршрутом и видом раздела — без id устройства,
  заголовков и тела. Метрика — встроенный счётчик
  `aspnetcore.rate_limiting.requests`, своего нет; экспорт — #27.
- **Проверка здоровья при обновлении** (`deploy/update.sh`, вариант A,
  выбран владельцем): тело и форма `/health` проверяются запросом изнутри
  контейнера api на петлю — раздел `local`, снаружи недостижимый; с хоста
  через опубликованный порт проверяется только, что порт отвечает HTTP
  (`200` или `429`).

## Отвергнуто

- **Лимитер до авторизации с одним разделом на всё.** Личности на этом
  месте ещё нет; любой, кто прошёл внешний периметр, держал бы владельца без
  доступа к дому каждое окно.
- **Раздел по IP, `CF-Connecting-IP` или `X-Forwarded-For`** — по причинам
  записи 0033; вдобавок раздел по подделываемому ключу плодит лимитеры без
  предела.
- **Один раздел `anonymous` на все анонимные конечные точки** — поток к
  `/health` закрывал бы обмен кода привязки.
- **Снять общий лимит с `/health`** (вариант B) — расходится с «все
  эндпоинты», а каждый внешний запрос к `/health` — неограниченные пробы
  компонентов.
- **Оставить проверку обновления с хоста как есть** (вариант C) — под
  внешним потоком к `/health` проверка получает `429`, и обновление
  откатывается.

## Цена

- **Общий `llm`-раздел.** Одно устройство или утёкший токен за
  `LlmRequestsPerMinute` запросов закрывает `/chat` и `/voice` для всех
  устройств до конца окна — и так каждое окно. Утёкший токен отзывается
  админ-эндпоинтом (README, «Утерян телефон»); устройство-источник видно по
  событиям его запросов с тем же `RequestId`.
- **Отказ политики тратит общий предел дважды.** Middleware ASP.NET Core 8
  после отказа политики повторяет захват путём ожидания, а фиксированное
  окно не возвращает разрешений: запрос, отклонённый политикой `llm`,
  списывает из общего раздела устройства два разрешения. При пределах по
  умолчанию (120 и 10) это заметно, только если устройство продолжает
  слать `/chat` сверх `llm`-предела; тогда оно раньше упирается и в общий.
  Счёт для устройства, которое повторяет `/chat` после `429`: принятый
  запрос стоит одно разрешение общего раздела, отказ политики `llm` — два.
  Десять принятых `/chat` оставляют 120 − 10 = 110 разрешений, их выбирают
  110 / 2 = 55 повторов после отказа `llm`. Дальше до конца окна устройство
  получает `429` от общего лимитера на всех маршрутах, а не только на
  `/chat` и `/voice`; каждый прочий запрос того же устройства в окне
  сокращает это число. Механизм закреплён тестом
  `LlmRejectionSpendsTwoPermitsOfDeviceGeneralPartition`: при общем пределе
  3 и `llm` 2 третий `/voice` отклоняет общий лимитер
  (`aspnetcore.rate_limiting.result = global_limiter`), а при общем 4 и
  `llm` 2 отказ политики `llm` на третьем `/voice` исчерпывает общий раздел
  — следующий `/state` того же устройства получает `429`.
- **`401` до лимитера.** Запрос без действующего токена к защищённому
  маршруту, как и запрос к несуществующему пути, получает `401` в
  авторизации и в общий лимит не засчитывается: каждый эндпоинт ограничен,
  а поток неаутентифицированных отказов — нет. Его ограничивает внешний
  периметр. Запрос с синтаксически верным, но чужим `Bearer` стоит
  обращения к хранилищу устройств (`DeviceTokenAuthenticationHandler`):
  поток таких запросов — нагрузка на базу, которую лимит не сдерживает;
  подбору токена это не помогает.
- **Анонимный раздел конечной точки общий для всех внешних клиентов.** Поток
  к `/health` сверх предела закрывает `/health` для всех внешних
  наблюдателей до конца окна; healthcheck контейнера и проверку обновления
  это не задевает — они в разделе `local`.
- **Проверка обновления с хоста** доказывает доступность порта, а не форму
  ответа через порт: форму проверяет запрос с петли контейнера.

## Условие пересмотра

Решение пересматривается новой записью, если выполнено хотя бы одно:

- публичный вход перестаёт идти только через туннель, или порт api перестаёт
  публиковаться на хост — адрес источника становится честным, и анонимный
  раздел по адресу перестаёт обходиться подделкой (как в 0033);
- в мобильном клиенте появляется несколько пользователей — общий на дом
  `llm`-раздел пришлось бы делить между ними;
- внешний вход приходит в api с петли — туннель или прокси в сетевом
  пространстве контейнера api (`network_mode: service:api`) или в сети
  хоста (`network_mode: host`): весь внешний анонимный поток уходит в
  раздел `local`, общий с healthcheck и проверкой обновления.
