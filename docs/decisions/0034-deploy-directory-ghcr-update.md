# 0034. Каталог развёртывания в дистрибутиве, образы из GHCR, обновление одной командой

**Статус:** принято
**Частично заменяет:** [0028](0028-docker-engine-in-wsl.md) — в части места
стека: стек больше не запускается из клона Windows, видимого в дистрибутиве
как `/mnt/<диск>/…`, и бэкап больше не идёт с `--cd <клон>`

## Контекст

Задача #162. По 0028 стек поднимался из рабочего клона владельца через мост
`/mnt/<диск>/…`, `api` собирался на месте, миграции владелец применял
руками SQL-скриптом с машины с SDK. Отсюда три проблемы: рабочий клон
влиял на боевой стек (правка, ветка или `docker compose up` в клоне
разработки пересобирали боевые контейнеры — проект различается по имени, а
не по каталогу); обновление было цепочкой ручных шагов без отката; хосту
нужны были SDK и `dotnet-ef`, а сборка на месте копила образы и кэш в
диске дистрибутива, который сам не сжимается.

## Решение

- **Каталог развёртывания** `/srv/domovoy` — отдельный git-клон в файловой
  системе `domovoy-engine`, только для запуска. Клонирует его root, тем же
  пользователем идёт обновление. Имя проекта прежнее (`domovoy`), тома
  именованные — прежние данные подхватываются без переноса.
- **Образы из GHCR.** На push в `main` workflow `publish-image.yml`
  собирает `domovoy-api` (стадия `runtime`) и `domovoy-migrate` (новая
  стадия: `postgres:16-alpine` с идемпотентным SQL миграций, ENTRYPOINT —
  `psql --single-transaction`) и публикует с тегами `sha-<коммит>` и
  `main`; на PR — то же без push. До push каждый образ проходит gitleaks по
  путям, которые добавляет наш Dockerfile, и по JSON конфига образа; новая
  точка COPY в финальной стадии добавляется в `scan_paths`
  `deploy/build-images.sh` той же правкой. Прогоны `main` идут каждый в
  своей группе concurrency: образ `sha-<коммит>` есть у каждого мерджа, а
  тег `main` при параллельных прогонах может остаться на прежнем коммите —
  `update.sh` его не читает. Пакеты после первой публикации владелец
  разово делает публичными.
- **Надстройка compose** `deploy/docker-compose.deploy.yml` через
  `COMPOSE_FILE` в `.env` каталога: у `api` — образ реестра и
  `build: !reset null`, плюс одноразовый сервис `migrate` (подключение
  только переменными `PG*`). Базовый `docker-compose.yml` не меняется.
  Ключи `COMPOSE_FILE`, `DOMOVOY_IMAGE_REPO`, `DOMOVOY_IMAGE_TAG` пишет
  только `update.sh`.
- **Обновление** — `deploy/update.sh` внутри дистрибутива; на Windows его
  зовёт тонкая обёртка `deploy/windows/update.ps1`. Проверки до первого
  изменения (код 1), затем по порядку: бэкап, файл состояния отката,
  `checkout` цели, синхронизация `.env`, управляемые ключи, pull, миграция,
  `up --wait` и `/health`, удаление файла состояния, чистка старых образов.
  Коды 0–4 у `update.sh`, 5 у обёртки — красный `engine-setup.ps1 -Check`
  после успеха. Шаги, коды и швы — шапка `deploy/update.sh`; порядок для
  владельца — README, «Обновление стека».
- **Откат** — по провалу между файлом состояния и `/health`: прежние
  управляемые ключи, прежний коммит, `up --wait`, `/health`. **Схема не
  откатывается**: прежний код работает на новой схеме, пока миграции
  следуют expand/contract. Файл состояния лежит в `.git` и переживает
  обрыв процесса: следующий запуск сначала доводит откат по нему.
- **Синхронизация `.env`** — `deploy/envfile.sh sync` по разметке над
  ключом `.env.example`: без разметки дописывается значение примера,
  `generate` — случайный секрет, `owner` — только строка «заполните KEY».
  Значения не печатаются; лишние ключи не удаляются.
- **Настройки хоста** (`engine-setup.ps1`, `install-schedule.ps1`,
  `measure-boot.ps1`) читают несекретные ключи `.env` каталога
  развёртывания через `envfile.sh get` с белым списком; задача бэкапа идёт
  с `--cd /srv/domovoy`. Пока каталога нет — прежнее поведение клона.
- **Диск и память ВМ.** `engine-setup.ps1 -Install` делает диск
  дистрибутива разреженным и пишет в `.wslconfig` `[experimental]`
  `sparseVhd=true` и `autoMemoryReclaim=gradual`; `-Check` проверяет атрибут
  файла диска, оба ключа и что стек поднят из каталога развёртывания.
- **Контракт для кнопки #163** — командная строка `update.sh`: аргументы,
  коды 0–4, префикс `update: `, блокировка, доведение прерванного прогона.

## Отвергнутые варианты

- **`image:` реестра в базовом `docker-compose.yml`** — стенд, CI и клон
  разработки стали бы зависеть от реестра и получили бы тег боевого образа.
- **`dotnet ef migrations bundle`** — нужна строка подключения целиком, путь
  не проверен на Postgres; идемпотентный SQL и `psql` проверены
  (`docs/tasks/12.md`).
- **SQL миграций в репозитории или генерация на хосте** — второй источник
  схемы, расходящийся молча, либо SDK на хосте.
- **Логика обновления в PowerShell** — не прогнать на ubuntu-раннере, а
  кнопка #163 зовёт обновление изнутри Linux.
- **Сторонние действия сборки и входа в реестр** — `docker login`, `build`,
  `push` покрывают задачу без новых звеньев цепочки поставки.
- **Скан базовых слоёв** — ложные срабатывания на файлах ОС; ослаблять
  правила ради чужих файлов нельзя.
- **Откат образа по красному `-Check`** — звенья хоста от образа не зависят.
- **Новое имя боевого проекта** — тома привязаны к имени, нужен перенос
  данных; ТЗ фиксирует проект `domovoy`.
- **`git fetch` в сухом прогоне** — меняет `.git`; превью берётся из
  временного неглубокого клона.
- **Путь бэкапа разностью каталогов `BACKUP_DIR`** — плановый бэкап за то
  же время кладёт туда свой каталог; путь берётся из строки
  `успех: <имя>`, которую печатает `backup.sh`.
- **Сквозной тест обновления в ci-heavy** — заменён живым прогоном на
  стенде агента с заведомо плохим образом.
- **Состояние отката только в памяти процесса** — обрыв оставил бы каталог
  на новом коммите без отката.
- **Дополнение к 0028** — меняется само место стека и способ обновления;
  прецедент — [0030](0030-wsl-nat-portproxy.md).

## Следствия

- Хосту стека хватает Docker: ни SDK, ни сборки образа.
- Рабочий клон на боевой стек не влияет; хост-сценарии по-прежнему
  запускаются из него. Команды по боевому стеку — в каталоге развёртывания
  (`wsl.exe -d domovoy-engine -u root --cd /srv/domovoy --exec …`).
- `restore.sh` о каталоге развёртывания не знает: берёт `COMPOSE_FILE` из
  `.env` каталога, где запущен; после восстановления — обновление. Перевод
  на образы реестра — вне #162.
- Ночной бэкап и обновление блокировкой не связаны; README просит не
  обновлять в окне бэкапа.
- `.wslconfig` с `[experimental]` действует на все дистрибутивы
  пользователя.
- Ручной путь обновления остаётся запасным — README, «Обновление стека».

## Принятый риск: подмена образа по тегу

Тег `sha-<коммит>` изменяем. Пакет GHCR, созданный `GITHUB_TOKEN`, доступен
на запись любому workflow этого репозитория, в том числе из ветки без
мерджа, а `update.sh` тянет образ по тегу без проверки происхождения.
Значит, push в любую ветку может перезаписать образ коммита `main`, и
следующее обновление его поставит.

Почему принято: ветки пушат только владелец и агент в его сессии; правка
`.github/**` поднимает уровень риска (`scripts/risk.json`) и идёт через
ревью. Закрытие — аттестация сборки (`attest-build-provenance`) и проверка
`gh attestation verify` по digest в `update.sh` — это новая зависимость в
workflow и `gh` в дистрибутиве движка.

Пересмотр — при первом из событий: появился участник с правом записи кроме
владельца; появилась кнопка обновления #163; найден подозрительный тег —
например, его digest не совпадает с прогоном `publish-image.yml` его
коммита.
