# 0034. Каталог развёртывания в дистрибутиве, образы из GHCR, обновление одной командой

**Статус:** принято
**Частично заменяет:** [0028](0028-docker-engine-in-wsl.md) — в части места
стека: стек больше не запускается из клона Windows, видимого в дистрибутиве
как `/mnt/<диск>/…`, и бэкап больше не идёт с `--cd <клон>`

## Контекст

Задача #162. По 0028 стек поднимался из рабочего клона владельца: compose
внутри `domovoy-engine` читал клон Windows через мост `/mnt/<диск>/…`,
собирал `api` из исходников (`docker compose up --build`), а миграции
владелец применял руками — SQL-скрипт генерировался на машине с SDK и
подавался в `psql` контейнера. Отсюда три проблемы:

- рабочий клон влиял на боевой стек: незакоммиченная правка, другая ветка
  или `docker compose up` в клоне разработки пересобирали боевые
  контейнеры — стек различается по имени проекта, а не по каталогу, а
  `.env.example` задаёт `COMPOSE_PROJECT_NAME=domovoy`;
- обновление — цепочка ручных шагов: бэкап, `git pull`, сборка, миграция,
  перезапуск, проверка; провал посередине оставлял стек в промежуточном
  состоянии, а отката не было;
- хосту стека нужен был SDK .NET с `dotnet-ef` ради одного SQL-скрипта, а
  сборка образа на хосте копила кэш и старые образы в диске дистрибутива,
  который сам не сжимается.

## Решение

### Каталог развёртывания

Стек живёт в каталоге развёртывания `/srv/domovoy` — в файловой системе
дистрибутива `domovoy-engine`, а не на диске Windows. Это отдельный
git-клон только для запуска: в нём не правят и не собирают. Клонирует его
root (`wsl -d domovoy-engine -u root`) — тем же пользователем, которым
`deploy/windows/update.ps1` зовёт `deploy/update.sh`, поэтому git не
отказывает по dubious ownership.

Имя проекта в каталоге развёртывания то же — `COMPOSE_PROJECT_NAME=domovoy`.
Тома именованные с префиксом проекта, поэтому каталог развёртывания
подхватывает прежние тома без переноса данных.

### Образы из реестра

Образы публикует CI — `.github/workflows/publish-image.yml`. На push в
`main` собираются два образа и уходят в GHCR с тегами `sha-<полный коммит>`
и `main`:

- `ghcr.io/<владелец>/domovoy-api` — стадия `runtime`
  `src/Domovoy.Api/Dockerfile`, цель по умолчанию, как и раньше;
- `ghcr.io/<владелец>/domovoy-migrate` — новая стадия `migrate`: образ
  `postgres:16-alpine` с SQL-скриптом миграций. Скрипт генерирует
  промежуточная стадия `migrations`: `dotnet ef migrations script
  --idempotent --no-transactions` той же версии, что EF Core проекта.
  `--no-transactions` убирает из скрипта собственные `START TRANSACTION` и
  `COMMIT` по миграциям; атомарность держит `psql -v ON_ERROR_STOP=1
  --single-transaction` — ENTRYPOINT образа: скрипт применяется целиком или
  никак.

На PR те же образы собираются и сканируются без push — чтобы сломанная
стадия или находка скана были видны до мерджа. Сборку, скан и push делает
общий сценарий `deploy/build-images.sh`: его зовут workflow и живой прогон
на стенде агента. Стороннего действия сборки в цепочке CI нет:
`docker login --password-stdin`, `docker build` и `docker push`.

**Скан образа.** До любого push каждый образ проходит gitleaks 8.30.1 —
правилами `.gitleaks.toml`, на PR взятыми с базы, а не из ветки. Сканируется
только то, что добавляет наш Dockerfile, — пути `/app` (образ `api`) и
`/migrations` (образ `migrate`), переменная `scan_paths` в шапке
`build-images.sh`, — и JSON конфига образа (ENV, метки, история) из архива
`docker save`. Базовые слои (`aspnet`, `postgres-alpine`) не сканируются:
это закреплённые upstream-образы, и правила проекта дают на их файлах
ложные срабатывания (замер #162: файлы dpkg, `openssl.cnf`, perl). Проверка
закрыта по умолчанию: путь из `scan_paths` не найден ни в одном слое или
пуст, нет JSON конфига — код 1, push не выполняется. **Новая точка COPY в
финальной стадии Dockerfile добавляется в `scan_paths` той же правкой** —
иначе её содержимое уйдёт в реестр без скана; об этом же комментарий над
стадиями `migrate` и `runtime`.

**Видимость пакетов.** Первый push создаёт пакеты `domovoy-api` и
`domovoy-migrate` приватными. Каталог развёртывания тянет образы анонимно,
поэтому после первой публикации владелец разово даёт обоим пакетам
публичную видимость в настройках пакета GHCR. До этого `update.sh`
отказывает до первого изменения: `docker manifest inspect` не видит образ.

### Надстройка compose каталога развёртывания

Базовый `docker-compose.yml` не меняется: CI, стенд агента и клон
разработки собирают `api` из исходников, как раньше. В каталоге
развёртывания compose читает ещё `deploy/docker-compose.deploy.yml` через
`COMPOSE_FILE` в его `.env`:

- у `api` — `image: ${DOMOVOY_IMAGE_REPO}/domovoy-api:${DOMOVOY_IMAGE_TAG}`
  и `build: !reset null` — собраться из исходников он не может (нужен
  compose 2.24 и новее, версию проверяет `update.sh`);
- одноразовый сервис `migrate` под своим профилем:
  `docker compose --profile migrate run --rm migrate`. Подключение к базе —
  только переменные `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`
  из `.env`: пароль не попадает в аргументы процесса.

Ключи `COMPOSE_FILE`, `DOMOVOY_IMAGE_REPO`, `DOMOVOY_IMAGE_TAG` —
управляемые: их пишет `update.sh`, руками они не правятся. В
`.env.example` они закомментированы отдельным блоком.

### Обновление — `deploy/update.sh`

Логика обновления — bash внутри дистрибутива. На Windows её зовёт тонкая
обёртка `deploy/windows/update.ps1`: проверяет по `wsl --list`, что
дистрибутив зарегистрирован и работает (до любого вызова `wsl -d`, который
поднял бы остановленный дистрибутив молча), что каталог развёртывания на
месте, и вызывает `update.sh` от root.

Проверки до первого изменения — отказ с кодом 1 и строкой
`update: отказ: <причина>`: каталог и его `.git`; блокировка `flock` от
параллельного запуска; движок и compose 2.24+; `curl`; `.env`; чистое
рабочее дерево; `postgres` и `homeassistant` проекта запущены и подняты из
этого каталога (метка `com.docker.compose.project.working_dir`; первый
запуск после переноса — с `--adopt`); целевой коммит (по умолчанию голова
`main` на origin); оба образа коммита есть в реестре; каталог `BACKUP_DIR`
доступен.

Изменения, строго в этом порядке:

1. бэкап `ops/backup/backup.sh`; путь нового каталога бэкапа печатается
   строкой `update: бэкап: <путь>`;
2. файл состояния отката;
3. `git checkout --detach` целевого коммита;
4. синхронизация `.env` по `.env.example` — `deploy/envfile.sh sync`;
5. все три управляемых ключа одним шагом, включая
   `DOMOVOY_IMAGE_TAG=sha-<цель>` — до pull и миграции: надстройка требует
   тег и у `api`, и у `migrate`, и `migrate` должен идти из образа
   целевого коммита;
6. `compose pull api migrate`;
7. `compose --profile migrate run --rm migrate` — схема;
8. `compose --profile ha up -d --wait` и `/health` на
   `127.0.0.1:<API_HTTP_PORT>` — 200 с телом формы стека;
9. чистка;
10. файл состояния удаляется.

Коды `update.sh`: 0 — обновлено или сухой прогон; 1 — отказ до первого
изменения; 2 — ошибка вызова; 3 — провал, откат выполнен, стек на прежнем
коммите отвечает; 4 — провал и отказ отката, нужен человек, путь бэкапа в
stderr. Обёртка добавляет код 5 (ниже).

`--dry-run` (`update.ps1 -DryRun`) печатает план — целевой коммит, образы,
команду бэкапа, превью синхронизации `.env`, чистку — и ничего не меняет:
ни `.git` (без `git fetch`; `.env.example` цели — из уже имеющегося объекта
или из временного неглубокого клона, который удаляется), ни `.env`, ни
контейнеры, ни образы.

### Откат

Откат — только по провалу шагов 2–8: `checkout`, синхронизации `.env`,
pull, миграции, `up --wait` или `/health`. Он возвращает прежние значения
трёх управляемых ключей (и их отсутствие после первого `--adopt`),
прежний коммит, поднимает стек (`up -d --wait`) и проверяет `/health`.

**Схема не откатывается.** Down-миграций нет; прежний код работает на
новой схеме, пока миграции следуют expand/contract (`.claude/CLAUDE.md`,
«Миграции БД»). Это условие отката, `update.sh` его не проверяет. Ключи,
дописанные синхронизацией `.env`, остаются: прежний код их не читает.

**Файл состояния** — `<каталог>/.git/domovoy-update.state`: внутри `.git`,
поэтому `checkout` его не трогает. Пишется после бэкапа и до `checkout`,
атомарно (временный файл, `umask 077`, `mv`): прежний и целевой коммит,
путь бэкапа, прежние значения управляемых ключей с отметкой отсутствия —
только несекретное. Удаляется после успеха и после завершённого отката.
Оборвался процесс — закрыто окно WSL, `wsl --shutdown`, `kill` — файл
остаётся, и следующий запуск `update.sh` (из обёртки или кнопкой #163)
сначала доводит откат по нему (код 3 или 4), а не начинает новое
обновление. Откат идемпотентен; сухой прогон о файле только сообщает.

**Проверка хоста после обновления.** После кода 0 обёртка запускает
`engine-setup.ps1 -Check`. Его звенья — firewall, portproxy, задачи,
`.wslconfig` — от образа не зависят, поэтому красный `-Check` образ не
откатывает: код обёртки 5, стек обновлён, звенья названы в выводе.

### Чистка

После успешного обновления из образов `<реестр>/domovoy-api` и
`domovoy-migrate` остаются текущий тег и тот, на котором стек работал до
обновления; локальный образ `<проект>-api` прежней сборки на месте
удаляется, если стек работал не на нём. `docker image rm` без `-f`. Кэш
сборки встроенного строителя — `docker builder prune --all --force`: он
общий для движка, и следующая сборка в клоне разработки внутри того же
движка пойдёт без кэша.

### Синхронизация `.env`

Новый коммит может принести новый ключ в `.env.example`. Разметка — строка
`# env-sync: generate` или `# env-sync: owner` прямо над ключом. Ключ,
которого нет в `.env`: без разметки — дописывается значением примера;
`generate` — случайным значением из 48 символов; `owner` — не дописывается,
а называется строкой «заполните KEY». Лишние ключи `.env` не удаляются.
Значения не печатаются ни в отчёте, ни в ошибках; сравниваются только
ключи.

### Настройки хоста — из `.env` каталога развёртывания

`engine-setup.ps1`, `install-schedule.ps1` и `measure-boot.ps1` получают
`-DeployDir` (по умолчанию `/srv/domovoy`). Порты, имя проекта и
`BACKUP_DIR` читаются из `.env` каталога развёртывания внутри дистрибутива
через `deploy/envfile.sh get` — только белый список несекретных ключей.
Задача бэкапа идёт с `--cd /srv/domovoy`, зонд замера — в каталоге
развёртывания, `-Uninstall` останавливает стек там же. Пока каталога нет
(хост до переноса), сценарии берут значения по умолчанию из
`docker-compose.yml`, задача бэкапа остаётся с `--cd <клон>`, и это
печатается; каталог есть, а `get` отказал — отказ. Сами хост-сценарии
по-прежнему запускаются из клона Windows: они настраивают хост, и
запускает их владелец явно.

### Изоляция от клона разработки

Имя проекта у каталога развёртывания и у клона разработки по умолчанию
одно. Защита от того, что клон разработки пересоздаст боевые контейнеры:

- `update.sh` без `--adopt` отказывает, если контейнеры проекта подняты из
  другого каталога;
- `engine-setup.ps1 -Check` получает звено «стек поднят из каталога
  развёртывания» по той же метке `working_dir`;
- шаг переноса в README: в клоне разработки — другое
  `COMPOSE_PROJECT_NAME` (например `domovoy-dev`), и только после того,
  как задача бэкапа переведена на каталог развёртывания.

### Диск дистрибутива и память ВМ

Образы, кэш сборки и база живут в `ext4.vhdx` дистрибутива, а виртуальный
диск сам не сжимается. `engine-setup.ps1 -Install`:

- делает диск разреженным — `wsl --manage domovoy-engine --set-sparse true`
  сразу после `--import`, а у уже зарегистрированного без атрибута
  `SparseFile` — в окне после `wsl --terminate` провижининга. Флаг
  `--allow-unsafe` не ставится. Отказ `--set-sparse` `-Install` не
  обрывает: остальные шаги доводятся, итоговый код ненулевой с текстом
  WSL, звено `-Check` «диск дистрибутива разреженный» красное, пока диск
  не разрежен; решение за владельцем;
- пишет в `%USERPROFILE%\.wslconfig` секцию `[experimental]`:
  `sparseVhd=true` (новые диски разреженные) и `autoMemoryReclaim=gradual`
  (ВМ отдаёт хосту освободившуюся память) — тем же планом, что
  `networkingMode` по 0030: прежний файл — копией, чужое значение этих
  ключей — отказ до первого изменения. Применяется после `wsl --shutdown`,
  его выполняет владелец.

`-Check` получает звенья: диск дистрибутива разреженный (атрибут файла, а
не обещание WSL), `sparseVhd`, `autoMemoryReclaim`, стек поднят из каталога
развёртывания, настройки каталога развёртывания.

### Вызов для кнопки обновления (#163)

Контракт вызова — командная строка `update.sh` внутри дистрибутива:
аргументы `--dir`, `--ref`, `--dry-run`, `--adopt`, `--image-repo`; коды
0–4; строки stdout с префиксом `update: `; без вопросов; блокировка от
параллельного запуска; прерванный прогон доводится следующим. Вызывающий
не важен — обёртка на Windows или кнопка изнутри Linux. Docker socket
контейнеру `api` для этого не монтируется; как кнопка доходит до вызова —
решает #163.

## Отвергнутые варианты

- **`image:` с тегом реестра в базовом `docker-compose.yml`.** Стенд агента
  собирает `api` в том же движке и получил бы тег боевого образа, а
  `down --rmi local` перестал бы его удалять; CI и клон разработки начали бы
  зависеть от реестра.
- **`dotnet ef migrations bundle` в образе.** Бандл строит хост приложения в
  момент миграции, ему нужна строка подключения целиком (пароль в
  окружении или аргументе), и этот путь на настоящем Postgres не
  проверялся. Идемпотентный SQL и `psql` уже проверены (`docs/tasks/12.md`,
  «Проверено»), а пароль `psql` получает переменной окружения.
- **SQL миграций, закоммиченный в репозиторий.** Второй источник схемы,
  который расходится с `Migrations/` молча; SQL из стадии сборки всегда
  того же коммита, что и образ.
- **Генерация SQL на хосте.** Требует SDK .NET и `dotnet-ef` на хосте, а
  хосту должно хватать Docker.
- **Логика обновления в `update.ps1`.** PowerShell с docker и git не
  прогнать на ubuntu-раннере CI, а кнопка #163 вызывает обновление изнутри
  Linux. Bash внутри дистрибутива тестируется подделками и годится любому
  вызывающему.
- **`docker/login-action`, `docker/build-push-action` и другие сторонние
  действия.** `docker login --password-stdin`, `build` и `push` покрывают
  задачу без новых звеньев в цепочке поставки CI.
- **Скан всех слоёв образа, включая базовые.** Правила проекта дают на
  файлах ОС базовых образов ложные срабатывания; ослаблять `.gitleaks.toml`
  ради чужих файлов нельзя, а закреплённые upstream-образы — не то, что
  может принести секрет проекта.
- **Откат образа при провале `engine-setup.ps1 -Check`.** Звенья `-Check` от
  образа не зависят; откат по ним менял бы рабочий образ из-за настройки
  хоста. Откат — по провалу `up --wait` и `/health`.
- **Новое имя боевого проекта (например `domovoy-prod`).** Тома привязаны к
  имени проекта — понадобился бы перенос данных через бэкап и
  восстановление; ТЗ фиксирует проект `domovoy`.
- **`git fetch` в сухом прогоне.** Меняет `.git` каталога развёртывания, а
  сухой прогон — «без изменений». Превью берётся из временного неглубокого
  клона.
- **Правка `backup.sh` ради машинной строки с путём бэкапа.** Путь
  получается без неё — разностью списков `domovoy-backup-*` в `BACKUP_DIR`
  до и после прогона.
- **Сквозной тест обновления в ci-heavy** (локальный реестр, три коммита,
  настоящий docker). Критерий — проверка прогоном с заведомо плохим
  образом, а не постоянная тяжёлая работа CI; она сделана одним живым
  прогоном на стенде агента.
- **Прежний коммит и ключи `.env` только в памяти процесса.** Обрыв между
  `checkout` и `up --wait` оставил бы каталог на новом коммите без отката;
  файл состояния в `.git` обрыв переживает.
- **Запись `DOMOVOY_IMAGE_TAG` после миграции, перед `up`.** Надстройка
  требует тег у `migrate`: при первом `--adopt` `compose run` упал бы на
  интерполяции, а при обычном обновлении применил бы SQL образа прежнего
  тега.
- **Дополнение к 0028 вместо новой записи.** Меняется само место стека и
  способ обновления; прецедент — [0030](0030-wsl-nat-portproxy.md).

## Следствия

- Хосту стека хватает Docker: ни SDK, ни `dotnet-ef`, ни сборки образа.
- Рабочий клон Windows на боевой стек больше не влияет — ни на образ, ни на
  `.env`, ни на бэкап, ни на настройки хоста. Хост-сценарии из клона
  запускаются по-прежнему.
- Команды по боевому стеку идут в каталоге развёртывания:
  `wsl.exe -d domovoy-engine -u root --cd /srv/domovoy --exec …`. Функция
  `docker()` из `~/.bashrc` работает в текущем каталоге Windows и после
  переноса попадает в проект клона разработки.
- `restore.sh` по-прежнему собирает `api` из исходников каталога, где
  запущен; после восстановления — обновление, которое переводит стек на
  образ реестра и убирает локальную сборку. Перевод `restore.sh` на образы
  реестра — вне #162.
- Ночной бэкап в 03:30 и обновление не связаны блокировкой. Миграция идёт
  одной транзакцией, и дамп видит согласованный снимок; README просит не
  запускать обновление в окне бэкапа. Общая блокировка — вне #162.
- `.wslconfig` с `[experimental]` действует на все дистрибутивы
  пользователя.
- Ручной путь обновления (миграция `psql`, `compose pull` и `up`) остаётся
  запасным — README, «Обновление стека».
