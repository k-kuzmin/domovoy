# 0017. Починка по замечаниям запускается комментарием, а не отзывом на PR

**Статус:** принято

## Решение

Прямое плечо цикла ревью замкнуто **комментарием `/fix`**.

Когда вердикт хотя бы одной половины ревью — `changes_requested`, job
`fix-request` в `agent-review.yml` пишет на PR комментарий `/fix` через
AGENT_TOKEN. `agent-fix.yml` получил третий вход — `issue_comment` с телом,
начинающимся на `/fix`.

Комментарий один на оба ревью: два запустили бы две починки одной ветки, и
вторая потратила бы попытку `fix/N` на уже исправленное.

Тот же комментарий остаётся рычагом человека — симметрично `/review` у ревью.

## Чего не хватало

Цикл был разомкнут в самом начале. `agent-review` печатал замечания через
`gh pr comment` и на этом заканчивался. Починку ждал `agent-fix` по событию
`pull_request_review` со `state == changes_requested`, но это событие не
возникало: **никто его не порождал.**

Запись 0016 замкнула возвратное плечо (после починки ревью начинается заново)
и оставила прямое открытым. Это его закрытие.

## Почему не формальный отзыв

Очевидное решение — научить `agent-review` делать
`gh pr review --request-changes`. Оно не работает, и это **проверено, а не
предположено**:

```
$ gh api repos/<owner>/<repo>/pulls/66/reviews -f event=REQUEST_CHANGES -f body='…'
{"message":"Unprocessable Entity",
 "errors":["Review Can not request changes on your own pull request"],
 "status":"422"}
```

GitHub запрещает запрашивать изменения в собственном PR. Автор PR здесь
**всегда** владелец: ветку пушит `agent-implement` через AGENT_TOKEN, то есть
от имени владельца токена. Отдельного аккаунта-бота в схеме нет и не
планируется — он потребовал бы второго места в организации и второго набора
секретов.

Следствие, которое стоит записать прямо: **путь `pull_request_review` в
`agent-fix` достижим только для человека,** поставившего «запросить изменения»
руками. Он оставлен как есть — это рабочий сценарий, — но цикл на него не
опирается.

## Что рассматривалось и отвергнуто

**Метка вместо комментария** (`review/changes-requested` плюс
`pull_request: [labeled]` у `agent-fix`). Отвергнуто: метки в этой схеме
делятся на разрешения человека и отчёты агента о состоянии, а здесь нужна
команда — «начни починку». Метка-команда сломала бы это деление, и таблица
меток в `docs/pipeline.md` перестала бы читаться однозначно. Плюс метку надо
снимать, иначе второй круг её не поставит заново, — состояние, за которым
надо следить.

**`repository_dispatch` или `workflow_dispatch`.** Отвергнуто: невидимо для
человека. Комментарий `/fix` виден в переписке PR, и по нему потом понятно,
почему началась починка. Диспатч оставляет только запуск в Actions.

**Оставить прямое плечо человеку** — то есть считать, что вердикт читает
владелец и сам решает, чинить ли. Отвергнуто владельцем при постановке: тогда
цикл не цикл, а два независимых шага, и «ревью → починка → ревью» существует
только в схеме.

## Следствия

- `agent-review.yml` — job `fix-request`, вердикт выведен из обоих ревью
  наружу через `outputs`;
- `agent-fix.yml` — третий вход `issue_comment`; шаг разрешения ветки
  переехал **до** `checkout`, потому что у `issue_comment` контекста ветки нет
  вовсе и `checkout` без неё взял бы `main`; проверка префикса `feat/` для
  этого входа переехала внутрь шага, где ветка уже известна; запасной ключ
  `concurrency` — номер PR;
- шаг «Ревью заново» срабатывает на оба входа по замечаниям, а не только на
  отзыв;
- `docs/rules/fix.md`, `docs/pipeline.md` — описан вход `/fix`.

Потолки не менялись: круги ревью — два (запись 0016), попытки починки — три.
Цепочка «ревью → `/fix` → починка → `/review` → ревью» упирается в потолок
кругов и заканчивается `agent/needs-human`.

Проверить на живом прогоне нельзя: цикл выключен (`vars.AGENT_LOOP_ENABLED` не
задана). Проверено разбором YAML, сверкой условий по всем трём событиям и
вызовом API, подтвердившим 422.
