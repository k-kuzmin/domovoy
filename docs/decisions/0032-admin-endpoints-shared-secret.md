# 0032. Админ-эндпоинты устройств под `/api/v1/admin` с общим секретом

**Статус:** принято
**Расходится с:** раздел 5 ТЗ

## Противоречие

Раздел 5 ТЗ описывает контракт `/api/v1` целиком под Bearer-токеном
устройства и не называет ни одного административного эндпоинта. Критерии #12 и
#13 при этом требуют выпуска кода привязки, списка привязанных устройств и
отзыва токена конкретного устройства. Кто вправе это делать, по какому адресу и
чем он аутентифицируется, ТЗ не говорит; записей решений об этом не было.

## Решение

- **Адрес.** Три эндпоинта под `/api/v1/admin`:
  `POST /api/v1/admin/pairing-codes` — выпуск одноразового кода привязки,
  `GET /api/v1/admin/devices` — список устройств с `last_seen_at`,
  `DELETE /api/v1/admin/devices/{id}` — отзыв токена устройства.
- **Схема доступа.** Отдельная Bearer-схема по общему секрету
  `Auth:AdminToken` из `IConfiguration`: локально — `dotnet user-secrets`, в
  стеке — `AUTH_ADMIN_TOKEN` в `.env`. Секрет в файлах проекта не хранится и не
  логируется.
- **Схемы не пересекаются.** Схемы аутентификации по умолчанию нет: каждую
  зовёт только политика, которая её называет. Токен устройства админку не
  открывает, админ-секрет не делает запрос устройством. Группа
  `/api/v1/admin` смаплена отдельно от группы `/api/v1`, иначе политики групп
  сложились бы и админ-запрос был бы обязан пройти ещё и схему устройства.
- **Не настроен — закрыто.** Пустой секрет или плейсхолдер — не ошибка старта:
  админ-эндпоинты отвечают `401` на любой запрос, а `docker compose up` на
  примерах поднимается (ТЗ 5.1.3, запись
  [0003](0003-validate-shape-not-secrets.md)).
- **Порог длины — 32 символа.** Настроенный секрет короче 32 символов — ошибка
  формы и отказ старта; сообщение называет ключ и порог, но не значение.
- **Сравнение** — SHA-256 предъявленного и настроенного значения
  `CryptographicOperations.FixedTimeEquals`: время ответа не подсказывает
  совпавший префикс и не зависит от длины секрета. Неудачная попытка — Warning
  в лог без предъявленного значения.
- **Ограничение частоты `/auth/device`** — встроенный
  `Microsoft.AspNetCore.RateLimiting`, фиксированное окно в минуту,
  `Auth:PairingAttemptsPerMinute` попыток (по умолчанию 5), **один общий
  раздел на весь эндпоинт**.

## Причина

- Первое устройство некому выпустить, если право выпуска лежит в токене
  устройства: роль admin в токене устройства не решает задачу начальной
  привязки. Общий секрет владельца работает с первого запуска.
- Отдельная схема, а не роль в общей, исключает класс ошибок «токен
  устройства случайно открыл админку»: схемы не делят ни хендлер, ни политику.
- Код привязки командой внутри контейнера — второй путь входа со своими
  тестами, а админ-доступ всё равно нужен для отзыва. Один путь вместо двух.
- Порог 32 символа: угадываемый секрет на публичном входе хуже закрытой
  админки. Отказ старта виден сразу, слабый секрет — нет.

## Компромисс общего раздела лимитера

Раздел лимитера один на весь `/auth/device`, а не по адресу источника:

- **По IP** раздел вырождается: за туннелем `RemoteIpAddress` у всех запросов
  — адрес `cloudflared`, раздел по IP становится общим, только неявно.
- **По `CF-Connecting-IP` или `X-Forwarded-For`** раздел обходится подделкой
  заголовка: порт api опубликован на хост (`docker-compose.yml`), и запрос в
  обход туннеля несёт любой заголовок.

**Цена:** тот, кто прошёл внешний периметр, может исчерпать окно и отложить
чужую привязку до конца окна, а продолжая слать запросы — держать обмен
закрытым каждое следующее окно. Код привязки он при этом не получает: перебор
упирается в тот же предел. Принято осознанно: привязка — редкое действие
владельца, отложить её дешевле, чем открыть перебор кодов разделом, который
обходится подделкой заголовка.

## Граница

- Админ-эндпоинты не анонимны: правило 7 раздела «Безопасность»
  `.claude/CLAUDE.md` эта запись не затрагивает, таблица анонимных
  эндпоинтов не меняется.
- Код привязки и токен хранятся только как SHA-256; открытое значение отдаётся
  один раз.
- Отзыв и его запись аудита — одна транзакция хранилища; в записи аудита есть
  `device_id`, значения токена нет.

## Условие пересмотра

Решение пересматривается новой записью, если выполнено хотя бы одно:

- появляется второй администратор или нужны раздельные права — общий секрет
  не различает, кто действовал;
- публичный вход перестаёт идти только через туннель, или порт api перестаёт
  публиковаться на хост — тогда раздел лимитера по заголовку источника
  становится честным;
- админ-действия появляются в мобильном клиенте — секрет пришлось бы хранить
  на устройстве.

## Следствия

- `Auth:AdminToken` входит в `SecretSettingPaths` теста
  `ConfigurationExampleTests.AppSettingsCarryNoSecrets`: заполненный
  админ-секрет в `appsettings.json` роняет тест.
- Сценарий «утерян телефон» в README — одна команда `curl` к
  `DELETE /api/v1/admin/devices/<device-id>` с плейсхолдерами хоста и секрета
  (запись [0001](0001-placeholder-hostnames.md)).
- Ограничение частоты — вторая мера границы записи
  [0025](0025-anonymous-device-pairing-endpoint.md), появившаяся вместе с
  реализацией обмена кода.
- Проверка токена устройства ходит в базу, а `GET /api/v1/health` стоит под
  политикой устройства. При недоступной базе подробный статус компонентов
  (NFR-OBS-3) не отдаётся: ответ — `503` `auth_unavailable`, а не отчёт с
  раздельным статусом БД. Регрессии нет — до #12 маршрут не открывался
  совсем, — но ограничение появилось с этой задачей. Другая схема доступа
  к `/api/v1/health` — отдельное решение человека.
