# 0032. Статусы доски ставит оркестратор сценарием `board.sh`, без workflow

**Статус:** принято

Кладётся поверх [0026](0026-human-led-pipeline.md), а не правит её: записи
решений не переписываются. Постановка — задача
[#159](https://github.com/k-kuzmin/domovoy/issues/159).

## Контекст

0026 убрала вместе с `status-sync.yml` и `scripts/set-project-status.sh` и
статусы доски («… метки `agent/*`, `plan/*`, `plan-review/*`, `review/*`,
`fix/*` и статусы доски»). Встроенные автоматизации доски были выключены, и
до 2026-10-15 у всех карточек стоял `Backlog`, а задачи после #56 на доску
не попадали вовсе. По доске не видно движения задач.

## Решение

**Статус карточки входит в процесс обвязки.** Его ставит оркестратор
локально сценарием `bash scripts/board.sh <номер issue> <статус>` в трёх точках
`.claude/CLAUDE.md`:

| Точка процесса (`.claude/CLAUDE.md`) | Статус |
|---|---|
| «Первые ходы», «Ветка на задачу одна»: вход в worktree **новой** ветки (созданной с `-b`) | `In progress` |
| «Рекомендованный порядок», п. 10: сразу после `gh pr create` | `Review` |
| п. 11, исход `MERGED`: до выхода из worktree | `Done` |

`In progress` ставится только на новой ветке: на найденной (возобновление,
починка на открытом PR) карточка могла уже стоять в `Review`, и вызов откатил
бы её. `Done` ставится до ExitWorktree: основное дерево может стоять на
коммите, где `scripts/board.sh` ещё нет.

Аргумент — номер issue, не PR. Номер PR сценарий отказывает кодом 2 до
добавления карточки: `gh issue view` на номер PR отвечает кодом 0 и отдаёт
node id PR, и без проверки на доске появилась бы отдельная карточка PR.

Сценарий находит доску, поле Status и его опции по имени при каждом вызове;
id нигде не записаны. Карточку он добавляет идемпотентной мутацией
`addProjectV2ItemById` (для карточки, которая уже на доске, она возвращает её
же id), ставит опцию и одним чтением сразу после установки подтверждает, что
на доске стоит именно она. Коды и вывод — шапка `scripts/board.sh`.

**Сбой не останавливает шаг процесса.** Ненулевой код у `In progress` и
`Review` уходит строкой в журнал задачи, раздел «Шаги». У `Done` — сообщением
человеку в сессии.

**Отступление от буквы #159 для `Done`.** Тело задачи говорит: «Сбой `gh` не
роняет шаг процесса, а пишется строкой в журнал». Для `Done` строки в журнал
нет: `Done` ставится после мерджа, журнал к этому моменту уже в `main`, а
коммитов после мерджа не бывает — `.claude/CLAUDE.md`, раздел «Git»:
«Журнал задачи приезжает в `main` в PR задачи; отдельных коммитов «шапка
приведена к состоянию после мержа» не бывает». Поэтому сбой `Done`
сообщается человеку в сессии.

## Почему цена 0026 здесь не возникает

Причина 0026 — цена: цикл в Actions, синхронизация двух режимов и самозащита
обвязки. Здесь ничего из этого нет:

- workflow нет, событий GitHub сценарий не слушает — его зовёт оркестратор в
  тех же шагах, которые он и так выполняет;
- токена в секретах CI нет: используется авторизация `gh` в сессии, которой
  нужен scope `project` (без него каждый вызов кончается кодом 1);
- режим один — локальный, синхронизировать не с чем.

## Совместимая настройка встроенных автоматизаций доски

Сценарий читает статус один раз сразу после установки. Автоматизация доски,
сработавшая позже, может статус перезаписать, и сценарий этого не увидит.
Гонку снимает настройка доски, а не ожидание в сценарии (решение владельца,
2026-10-15). Настраивает владелец в интерфейсе доски; сценарий настройку не
проверяет. Совместима такая:

- «Auto-add» и «Item added → Backlog» срабатывают при заведении issue,
  задолго до ветки задачи, и `In progress` не затирают;
- «Item closed» и «Pull request merged» ставят `Done` — совпадает с точкой
  `Done`;
- «Pull request linked to issue» выключена или ставит `Review` — совпадает с
  точкой `Review`.

При такой настройке ни одна автоматизация не ставит статус, отличный от
статуса процесса в момент его вызова. На момент записи автоматизации
выключены, кроме «Auto-add sub-issues».

## Пределы

- Статус не ставится, если вызов пропущен: точку держит правило
  `.claude/CLAUDE.md`, а не механика.
- Сценарий читает статус один раз сразу после установки: расхождение, видимое
  в этот момент, — код 1; асинхронную перезапись позже он не ловит. Это
  снимается совместимой настройкой доски выше, а не сценарием.
- Ветка «карточки нет — добавить» вживую не проверялась: все issue уже на
  доске. Её держат сценарии `scripts/board.test.sh` с подставным `gh` и
  идемпотентность `addProjectV2ItemById`.
- Статусы `Backlog` и `Ready` процесс не ставит; сценарий их принимает — для
  ручной починки доски.

## Расхождение с ТЗ обвязки

ТЗ обвязки (`tz-pipeline/TZ-pipeline.md`, вне репозитория, «Фаза 8») требует:
«Синхронизация статусов в GitHub Projects v2: статус двигает workflow по
событиям (метки, открытие PR, закрытие issue), не агент». Здесь статус
двигает агент-оркестратор. Workflow-синхронизацию убрала уже 0026, так что
расхождение с этим пунктом существовало и до этой записи; механизм выбрал
владелец в задаче #159.

## Что рассматривалось и отвергнуто

**Вернуть `status-sync.yml`.** Отвергнуто: это ровно тот механизм, который
убрала 0026, — цикл в Actions и токен со scope `project` в секретах CI.

**Строки `gh project item-edit` прямо в `.claude/CLAUDE.md`, без сценария.**
Отвергнуто владельцем: id поля и опций оказались бы в тексте.

**Ожидание и повторная установка в сценарии при расхождении прочитанного
статуса.** Отвергнуто владельцем: перезапись, пришедшая позже окна ожидания,
окном всё равно не ловится, а пауза ложится на каждый вызов. Гонку снимает
настройка доски.

**Предупреждение и код 0 на неизвестном статусе, как в старом
`set-project-status.sh`.** Отвергнуто: критерий #159 требует понятного отказа
с ненулевым кодом. Терпимость к сбою — правило точки вызова, а не сценария.
