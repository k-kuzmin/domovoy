# Конвейер

Как устроена работа над задачей: кто её ведёт, где лежат правила, какие
скрипты и проверки стоят по дороге и что выставляется в репозитории руками.
Документ — обзор устройства. Сами правила здесь не повторяются: у каждого одно
место, и ссылка ведёт туда.

Обоснование, что заменено из прежних записей, и пределы схемы — запись
[0026](decisions/0026-human-led-pipeline.md).

## Кто ведёт задачу

**Автоматического бота нет.** Задачу всегда ведёт человек с агентом в Claude
CLI. Основная сессия — **оркестратор**: выбирает шаги под задачу, поручает
объёмное субагентам, склеивает результат и отвечает за него. GitHub остаётся
местом, где лежат задачи и где на PR отрабатывает CI.

| Кто | Что делает |
|---|---|
| Человек | ставит задачу, отвечает на сработавшие триггеры, смотрит план и резюме, когда требует маршрут; **мерджит** |
| Оркестратор | ведёт задачу по рекомендованному порядку, пишет журнал и план, публикует наружу (комментарии, PR), закрывает задачу после мерджа |
| Шаги — `.claude/agents/step-*.md` | триаж, план, реализация, ревью корректности и безопасности, починка — каждый с чистым контекстом и своим файлом правил |
| Совет — `.claude/agents/advisor-*.md` | ревью плана, а по признакам и диффа: скептик, инженер, страж, прагматик |

Рекомендованный порядок шагов, первые ходы по задаче, триггеры «позвать
человека», минимум маршрута, потолок кругов и делегирование —
[`.claude/CLAUDE.md`](../.claude/CLAUDE.md), раздел «Как ведётся задача».
Таблица маршрута по уровню, таблица шагов (условие входа, результат, когда
пропускается) и признаки совета — [`docs/rules/README.md`](rules/README.md).

Конвейер — рекомендация, а не сценарий: скилла или скрипта с зашитой
последовательностью шагов нет. Пропущенный или добавленный шаг записывается
строкой в журнал.

## Где правила

| Файл | Отвечает на вопрос | Кто читает |
|---|---|---|
| `.claude/CLAUDE.md` | что в проекте можно и нельзя, как вести задачу | любая сессия — CLI загружает его сам |
| `docs/rules/README.md` | какие шаги нужны задаче, сколько кругов, собирать ли совет | оркестратор, выбирая маршрут |
| `docs/rules/<этап>.md` | на что смотреть на конкретном этапе | тот, кто выполняет этап, — в момент, когда к нему приступает |
| `docs/decisions/` | почему так, а не иначе | при сомнении «это специально?» |

Какой файл этапа когда открывать — указатель в `.claude/CLAUDE.md`, раздел
«Правила этапа: когда открывать».

Гарантированно читается только `.claude/CLAUDE.md`. Правила этапа держатся
тремя вещами: первая инструкция определения субагента — прочитать файл своего
этапа; впрыск правил дописывает её в промпт при запуске; ссылаться на правило
можно только после `Read` его файла в этой сессии. Это не гарантия: хук видит
действия, а не решение «перехожу к плану».

## Впрыск правил

Хук напоминает правило в момент, когда рука занесена над местом, которое
правило защищает, — и кладёт в контекст суть и путь к файлу правила.

| Файл | Что это |
|---|---|
| `.claude/hooks/rule-injector.sh` | предфильтр на чистом bash: отсеивает вызовы, к которым ни одно правило не относится |
| `.claude/hooks/rule-injector.py` | движок: сопоставляет вызов с таблицей, ведёт флаги «уже напоминал» и счётчик правок |
| `.claude/hooks/rules-map.json` | таблица правил проекта: на что срабатывает, что напоминает, `doc` — файл правила |
| `.claude/hooks/tests/` | тесты движка и таблицы — `python3 -m unittest discover -s .claude/hooks/tests -v` |

Подключается в `.claude/settings.json` — матчером на каждое имя инструмента и
на событие `UserPromptSubmit`. Три способа срабатывания:

- `PreToolUse` — на действие: запись в миграции, `AllowAnonymous`, первый
  `git push` в сессии, первая правка кода или обвязки и так далее;
- `UserPromptSubmit` — на формулировку в реплике человека;
- `for_subagents` — при запуске субагента дописывает в промпт правила его
  этапа (`step-rules`); у советников формы «для всех» нет.

Отдельно — счётчик собственных правок оркестратора: на 4-м и 7-м разном файле
за сессию напоминает о пороге делегирования; `docs/tasks/**` не считает.

Состояние хука — `.claude/hooks/.rule-flags/` и `.claude/hooks/.python-path` —
в `.gitignore`. Нужен python 3; без него хук пропускает вызов, а не отказывает.
Напоминание правилу положено, только если нарушение тихое — не падает, а молча
портит данные или процесс; шумное ловит сборка. Поле `note` в таблице — условие
и указание открыть файл, а не пересказ нормы, поэтому синхронизировать
таблицу с правилами нечего.

Пределы — чтение хук не видит, новая форма команды без строки в предфильтре
молча не срабатывает, хук исполняет код рабочего дерева — в записи
[0026](decisions/0026-human-led-pipeline.md). Практическое следствие одно:
**чужую ветку (`gh pr checkout`) сессией с подключённым хуком не открывать.**

## Скрипты

Все — в `scripts/`, bash, у каждого свой файл сценариев `scripts/<имя>.test.sh`.
Ни один не блокирует работу по уровню: скрипт сообщает, решает человек и
оркестратор.

| Скрипт | Вызов | Что делает |
|---|---|---|
| `risk.sh` + `risk.json` | `bash scripts/risk.sh plan docs/tasks/<N>.plan.json`, `bash scripts/risk.sh diff origin/main HEAD` | уровень `low`/`medium`/`high` и причины: пути и слова в добавленных и удалённых строках; в режиме `plan` — пути из `files[].path` и их число |
| `council.sh` | `bash scripts/council.sh <plan\|diff> <артефакт> .council/<N>/<режим>-<круг> [прошлый-хеш]` | детерминированная сводка вердиктов совета: отбрасывает замечания без доказательства, печатает принятые, итог и `hash=` набора |
| `plan.sh` + `plan-schema.json` | `bash scripts/plan.sh validate <файл>`, `bash scripts/plan.sh render <файл>` | форма плана; рендер — то, что читает человек |
| `guard-lite.sh` | `bash scripts/guard-lite.sh origin/main HEAD` | гейт целостности: подавления, удалённые тесты, разрушительная миграция в `Up()`, мусор и подписи в диффе |
| `review-comments.sh` | `bash scripts/review-comments.sh <номер PR>` | построчные замечания ревью — те, что `gh pr view --comments` не отдаёт |

**Конфиг риска читается с `origin/main`,** а не из дерева: дифф не ослабляет
правило, по которому его оценивают. Пока файла на `origin/main` нет, берётся
дерево, и это печатается причиной. Таблица путей и слов — сам `scripts/risk.json`;
пути в нём разложены по именованным группам, и причина называет группу.

**Коды `council.sh`** и что сводка отбрасывает — шапка `scripts/council.sh`.
Совет может блокировать, но не одобрять: зелёный итог не заменяет триггеров.

## Совет

Четыре определения в `.claude/agents/`: `advisor-skeptic`, `advisor-engineer`,
`advisor-constitution` (страж), `advisor-pragmatist`. Модель задана в каждом
явно. Когда совет собирается и в каком составе — `docs/rules/README.md`.

Как запускаются советники и что получают на вход —
[`.claude/CLAUDE.md`](../.claude/CLAUDE.md), раздел «Делегирование», и
`docs/rules/README.md`, «Вход»: Bash у советников нет, вход оркестратор
кладёт файлами в `.council/<N>/<режим>-<круг>/in/`. Ответы советников
оркестратор сохраняет в
`.council/<N>/<режим>-<круг>/<роль>.json` (каталог в `.gitignore`) и читает
сводку `council.sh`, а не составляет её сам. В журнал уходят итог, число кругов
и хеш набора.

Схема вердикта и правила формы — в самих определениях `advisor-*.md`.

## Журнал и план

`docs/tasks/<N>.md` — журнал, `docs/tasks/<N>.plan.json` — план; оба в ветке
задачи, едут в PR и остаются в `main`. Что в журнале и когда он обновляется —
[`docs/tasks/README.md`](tasks/README.md), шаблон —
[`docs/tasks/TEMPLATE.md`](tasks/TEMPLATE.md). Меток стадии нет; стадия и
счётчики кругов — в шапке журнала.

## PR и CI

Ревью диффа идёт **по ветке, до PR**. PR открывает оркестратор после ревью,
когда журнал закоммичен и запушен, и сразу не черновым. Шаблон тела —
[`.github/pull_request_template.md`](../.github/pull_request_template.md):
«Выбрано и отвергнуто», расхождение с планом, «Попутно». Дальше — ревью Copilot
после каждого пуша. Мердж делает человек.

| Workflow | Работа | Когда | Что проверяет |
|---|---|---|---|
| `CI (fast)` | Сборка, стиль, тесты | PR и push в `main` | стиль, сборка без предупреждений, тесты с архитектурными, порог покрытия 50 %, сценарии скриптов обвязки и тесты впрыска |
| `CI (fast)` | Гейт целостности | только `pull_request` | `scripts/guard-lite.sh` по диффу PR; меток не читает |
| `CI (fast)` | Уязвимые пакеты | PR и push в `main` | известные уязвимости в пакетах |
| `CI (heavy)` | Стек поднимается на примерах конфигурации, CodeQL | новый коммит PR, push в `main` | стек на `.example`-файлах, статический анализ |
| `gitleaks` | Поиск секретов в истории, сообщения коммитов | любой push и PR | секреты; запрет трейлеров соавторства и подписей инструмента |

Локально до коммита работают хуки `.githooks/`: `pre-commit` (gitleaks) и
`commit-msg` (Conventional Commits, запрет соавторства).

Гейт берётся из ветки PR, поэтому `guard-lite.sh` правится тем же диффом,
который проверяет. Это принятый предел; правка гейта поднимает уровень до high
и зовёт человека (запись 0026).

## Права и ruleset

**`.claude/settings.json`** — проектные права для `Bash` и `PowerShell`:

- `deny` — мердж PR, force-push и push в `main`, применение миграций к базе,
  секреты (`dotnet user-secrets`, `gh auth token`, переменные окружения,
  `docker compose config`, чтение каталога секретов и `.env`);
- `ask` — `gh issue create` (задачу агент заводит только по явной просьбе) и
  `gh pr create` (человек видит команду и тело PR).

Список шаблонов — сам файл. Это **страховка от случайности, а не граница**:
шаблоны сопоставляются по префиксу, и формы команд, которые они не ловят,
перечислены в записи 0026. Миграции к базе и секреты человек запускает сам, в
сессии — через `!`.

**Ruleset на `main`** — граница там, где граница нужна: запрет force-push и
удаления ветки, изменения только через PR. Закрывает push-формы, которые не
ловит `deny`. Обязательных чеков не задаёт.

## Что выставляется руками

Ни один пункт не задаётся файлом в репозитории.

- [ ] `git config core.hooksPath .githooks` — на каждой машине, где делаются
      коммиты. Без этого `pre-commit` и `commit-msg` не подключаются.
- [ ] python 3 и `jq` в системе. `jq` читают `plan.sh`, `review-comments.sh`,
      `risk.sh` и `council.sh`; python 3 — впрыск правил.
- [ ] Ruleset на `main`: запрет force-push и удаления, изменения только через
      PR. Проверка — `gh api repos/{owner}/{repo}/rulesets`.
- [ ] Оставить только squash-мердж, включить автоудаление веток. Auto-merge не
      включать: мердж делает человек.
- [ ] Галочку «Require review from Code Owners» не включать: GitHub не
      засчитывает апрув автора PR, а единственный code owner здесь — автор.
      `.github/CODEOWNERS` только зовёт владельца на ревью.

**Определения агентов, права и хуки читаются на старте сессии.** Правка
`.claude/agents/`, `.claude/settings.json` или `.claude/hooks/` вступает в силу
в новой сессии; проверять её — живым прогоном там же.
