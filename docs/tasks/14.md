## Решения

**Триаж (2026-11-11).** Вердикт `ready=false`: два вопроса владельцу. В `main`
`POST /api/v1/chat` — заглушка 501
(`src/Domovoy.Api/Endpoints/ApiV1Endpoints.cs:34`); быстрый путь
(`FastRouter`, `FastPathRunner`) и единый формат ошибок (`ApiError`,
`ApiErrorResults`) уже есть. Утверждения триажа сверены с кодом `main`.
Ответы владельца (2026-11-11):

1. «curl из README управляет реальным устройством» — **стенд агента + HA
   владельца после мерджа**: агент проверяет curl из README на стенде с
   демо-устройствами; владелец после выкатки один раз прогоняет тот же curl
   на домашнем HA, и задача закрывается только после его проверки.
2. Объём — **один PR**, без дробления: основная часть (быстрый путь, формат
   ошибок) уже в `main`.

С ответами вопросов нет — задача готова к плану.

**Совет по плану, круг 1 (2026-11-11).** `council.sh` — код 0, блокеров
нет: страж, инженер, скептик — `no_objections`, прагматик — `another_round`.
Принято и внесено в план:
- [major] прагматик — не выносить `CurlCommand`/`BashBlock` в отдельный
  `ReadmeCurl.cs`, а сделать их `internal` на месте в `HomeEndpointsTests`:
  вынос критерий не требует; файлов 12 → 11.
- [nit] скептик — в теорию `ChatRejectsMalformedRequest` добавлено тело из
  невалидных байт UTF-8 → 400.
- [nit] скептик — «Готово» подтверждает вызов, а не результат: на стенде
  состояние сверяется через `GET /api/v1/state`, это уже в плане; при
  передаче владельцу — просить сверить смену состояния, а не только текст.
- [nit] прагматик — перенос таблицы статусов оставлен (keep), согласен.
- [nit] прагматик — свести теории границ длины в одну: уже одна теория
  `ChatRejectsMalformedRequest`, отдельных методов нет.

Второй круг не нужен: блокеров не было, правка плана уменьшает его. Уровень
medium — человек план не смотрит (минимум маршрута).

**Пределы длины** `text` ≤ 2000 и `conversation_id` ≤ 128 — ни ТЗ, ни задача
их не задают; спросить не у кого до реализации, принято по плану, совет не
оспорил.

**Срез `core` (2026-11-11).** Перенесён cherry-pick, файлы — ровно три
файла среза. Решения среза вне контракта: чтение без имени в allow-list —
ответ `Payload` без точки; `Matched` без `Match`/`Result` — нарушение
инварианта `FastPathOutcome`, `InvalidOperationException` (эндпоинт отдаст
500); `Elapsed` — разность `GetUtcNow()`, потому что тестовые часы
`ManualTimeProvider` не переопределяют `GetTimestamp`. Красный прогон до
реализации — 6 из 6 упали; тест DI упал на блокировке DLL политикой
управления приложениями Windows (`0x800711C7`), а не на отсутствии
регистрации — падения по существу у него не видели. Литерал адреса в тесте DI
заменён на `DomovoyApiFactory.UnreachableHaBaseUrl`.

**Срез `api` (2026-11-11).** Перенесён cherry-pick, три коммита (два
`refactor`, один `feat`), файлы — ровно восемь файлов среза. Расхождения с
планом (все — сверх плана, не вместо):
1. Тест `ChatAcceptsLimitLengths` — включительная граница 2000/128.
2. В теории `ChatTranslatesHaRefusalByStatusTable` седьмой случай —
   `ha_rejected` с пустым сообщением (пункт контракта о замене).
3. Пустое сообщение отказа заменяется на «Запрос не выполнен.» (тот же текст,
   что у 500); план фиксированный текст не называл.
4. Теория `ChatRejectsMalformedRequest` шире плана: невалидный UTF-8 внутри
   строки, `{}`, только `conversation_id`, `text: null`.
5. Защитные ветки 500 сверх контракта: поток без `done`, нет claim
   `NameIdentifier`; тестов на них нет.
6. Тест README не сверяет `/state` до и после — это стендовая часть A-curl.

Срез поймал дефект своим же тестом: невалидный UTF-8 внутри строки давал
500 (`JsonElement.GetString()` бросает `InvalidOperationException`) — исправлено
`TryReadString`.

**Уровень по диффу — high** при medium по плану: слова аутентификации в
`ChatEndpointTests.cs` (`Bearer`, `authoriz…`, `device-token…`, `Ha:Token`,
`ApiKey…`) и размер (13 файлов, 1561 строка). Сработал триггер «уровень по
диффу high при уровне по плану ниже»; маршрут ужесточён до high: два круга
ревью диффа, совет по диффу, резюме владельцу до PR — в нём и вопрос по
триггеру.

**Живая проверка: пример README из Git Bash.** Кириллица в `-d` ушла не в
UTF-8 — сервер ответил 400 `invalid_request` (так и должен). С телом из
UTF-8 файла (`--data-binary @файл`) всё прошло. Это свойство Git Bash на
Windows, а не сервера; риск был записан в плане.

## Отвергнуто

- Дробление на подзадачи по 2–8 ч — отклонено владельцем: быстрый путь и
  формат ошибок уже в `main`, остаётся связка с эндпоинтом.
- Приёмка только на HA владельца с закрытой #4 — отклонено владельцем:
  агент проверяет на стенде, владелец — после мерджа.
- Общий тестовый файл `ReadmeCurl.cs` — совет (прагматик): вынос не нужен
  критерию, `internal` на месте дешевле.
- JSON на любой `Accept` — на этапе 2 тот же клиент получил бы SSE вместо
  JSON (ТЗ, раздел 5: SSE по умолчанию); выбран 501 без
  `Accept: application/json`.

## Шаги

- Воспроизведение пропущено — задача не баг.
- Совет по плану — по маршруту medium (скептик, инженер, страж) плюс
  прагматик: файлов 12 > порога 11. Сработавшие признаки: контракт API
  (тело ответа `/chat`, режим по `Accept`); общий механизм — перенос таблицы
  «код слоя Ha → HTTP-статус», греп: один вызывающий, `HomeEndpoints.cs`;
  новая функциональность (первая реализация `IOrchestrator`). Глобального
  переключателя нет. Ревью плана на корректность не зовётся — совет есть.
- Реализация — субагентами, два среза (`core`, затем `api`): 11 файлов и
  сотни строк — выше порога делегирования.
