## Решения

**Две задачи в одном PR.** Владелец (2026-10-15): #12 и #13 — одним PR,
ведущая #12. Одна ветка, один журнал и один план под номером 12; #13 — часть
плана, PR закрывает обе. Дробление, которого требует тело #12 (оценка больше
8 ч), — срезами плана, а не отдельными PR.

**Триаж #12.** Не готова: открыты источник кода привязки, ограничение
частоты и объём. Критерий проверяем, кроме «токен отсутствует в артефактах
клиента» — клиента ещё нет (#38), способа проверки сейчас нет. Расхождение с
ТЗ раздела 5 (анонимный `/auth/device`) уже принято записью
[0025](../decisions/0025-anonymous-device-pairing-endpoint.md).

**Триаж #13.** Не готова: токены не выдаются (#12), `EfAuditLog.WriteAsync` —
заглушка (реализация — #16), схема доступа к админ-эндпоинту не задана ни ТЗ,
ни записями решений. Адреса админ-эндпоинта в контракте ТЗ раздела 5 нет.
Факты сверены по дереву: заглушка в `src/Domovoy.Data/EfAuditLog.cs`, в
`DomovoyDbContext` нет ни одного `DbSet`, миграций нет — задача заводит
первую схему БД.

**Ответы владельца на вопросы триажа (2026-10-15):**

- Код привязки выпускает админ-эндпоинт под `/api/v1/admin/…`: одноразовый,
  с ограниченным временем жизни. Доступ тот же, что у отзыва.
- Доступ к админ-эндпоинтам — отдельный админ-секрет из `IConfiguration`, своя
  Bearer-схема. Без настроенного секрета админ-эндпоинты закрыты. Схема
  доступа и адрес админ-эндпоинтов не описаны в ТЗ — уезжают записью в
  `docs/decisions/`.
- Ограничение частоты для `/auth/device` входит в PR — встроенный
  `Microsoft.AspNetCore.RateLimiting`, новой зависимости нет. Это вторая мера
  границы записи 0025.
- Аудит отзыва — минимальная запись: таблица и рабочий
  `EfAuditLog.WriteAsync`. Ретенция, политика в README и запись из `/chat` и
  `/action` остаются за #16; пересечение — в «Попутно» тела PR.

**Совет по плану, круг 1.** Код 0, блокеров нет; 8 major и 4 nit. По
замечаниям план исправлен: схема по умолчанию снята (каждую схему зовёт своя
политика, анонимные маршруты в хранилище не ходят); 503 `auth_unavailable`
выдаёт challenge по типу отказа, а не запись в ответ из аутентификации; отзыв
и запись аудита — одна транзакция хранилища; админ-секрет — не короче 32
символов или не настроен; сбой обновления «последнего обращения» запрос не
роняет; тест README сведён к строковой проверке, два обхода маршрутов — к
одному. Общий раздел лимитера `/auth/device` оставлен осознанно: раздел по IP
подделывается при опубликованном порте, компромисс уходит в запись 0032.
Не принято: константа вместо настройки лимита — на ней держатся тесты.

**Совет по плану, круг 2.** Код 0, блокеров нет; инженер и страж — без
возражений. Принято: тело `/auth/device` проверяется до хранилища — `name` не
длиннее 64 символов, иначе 400 `invalid_request` и код не тратится (тест
`PairingWithTooLongNameIsInvalidRequest`); очистка кодов привязки — в
`out_of_scope`. Не принято предложение прагматика снять 503 `auth_unavailable`
и порог длины админ-секрета: это ответы на major скептика и инженера круга 1,
механизм инженер во втором круге принял. Рабочий `EfAuditLog.WriteAsync`
остаётся — ответ владельца. Третий круг не собирался: единственный принятый
major закрыт правкой контракта и тестом, а запас общего предела 5 нужен на
два круга ревью диффа.

**План согласован владельцем (2026-10-15).** Развилка карточки: первую
миграцию применяет человек — командой из README (`dotnet ef migrations script
--idempotent` в `psql` контейнера), приложение миграций на старте не применяет.

**Срез core перенесён.** Расхождение с контрактом: регистрация
`DeviceAuthService` в `AddDomovoyCore` снята срезом — без зарегистрированного
`IDeviceStore` проверка DI на старте хоста роняет 20 тестов. Строка поручена
срезу `api` (его тестовая фабрика подменяет хранилище); `EfDeviceStore`
регистрирует срез `data`. Сверх контракта: необязательный `CancellationToken`
в методах сервиса, константы `RevokeDeviceAuditToolName` и
`MinAdminTokenLength`; пустой код и пустой токен в хранилище не идут.

## Отвергнуто

- `Database.MigrateAsync` на старте — старт api зависит от базы, тестам нужен
  выключатель; владелец выбрал применение человеком.
- Два журнала и два плана на одной ветке — владелец выбрал одну ведущую задачу.
- Роль admin в токене устройства — первое устройство некому выпустить.
- Код привязки командой в контейнере — второй путь входа со своими тестами,
  а админ-доступ всё равно нужен для отзыва.
- Взять #16 целиком — три задачи в одном PR, около 17–32 ч.

## Шаги

- Триаж #12 и #13 — двумя запусками step-triage параллельно; вопросы обоих
  сведены в один вопрос владельцу.
- Совет по плану — по маршруту high (скептик, инженер, страж, прагматик).
  Сработавшие признаки: контракт API и миграция; общий механизм —
  аутентификация на всех маршрутах `/api/v1` (группа `RequireAuthorization` в
  `ApiV1Endpoints.cs`); новая функциональность. Глобального переключателя нет.
- Карточка развилки: `fork: true` — применение первой миграции (человек
  командой из README или само приложение на старте). Вопрос владельцу — после
  исправления плана по совету.
- Совет по плану, круг 2 — правки круга 1 меняют механизм аутентификации
  (схемы, ответ 503, транзакция отзыва).

- Рендер плана (около 129 тыс. символов) комментарием в issue не
  публиковался: больше предела комментария 65 536; владелец смотрел его в
