(объём) не пройден: в задаче шесть поставок (образ в GHCR, каталог

отказ при неработающем движке — их назначает план (контракт приёмки); пункты
про миграцию и чистую машину требуют среды — стенд #164 и владелец.
Расхождение для плана: перенос стека с `/mnt/<диск>` в файловую систему
дистрибутива расходится с записью 0028 («Клон там виден как `/mnt/<диск>/…`»)
— нужна новая запись в `docs/decisions/`.

**Объём (2026-10-16).** Вопрос владельцу: разбить задачу и с чего начать.
Ответ: «Не разбивать» — вся задача одним PR.

**Указание владельца (2026-10-16).** «В целом действуй по своим
рекомендациям»: развилки решает оркестратор по своей рекомендации и пишет
сюда. Живые проверки (миграция с бэкапом, откат с плохим образом,
синхронизация `.env`, отказ при неработающем движке) — на тестовом стенде
#164, не на боевом стеке.

**План.** Подробно — [`162.plan.json`](162.plan.json). SQL миграций —
`dotnet ef migrations script --idempotent` в образе `migrate`, применяется
psql; стек — отдельный клон `/srv/domovoy` в `domovoy-engine`; логика
обновления — `deploy/update.sh`, обёртка `deploy/windows/update.ps1`; запись
0034 частично заменяет 0028.

**Развилка: откат по чему.** Откат образа — только по провалу `up --wait` и
`/health`; красный `engine-setup.ps1 -Check` — код 5 без отката. Выбрал
оркестратор по рекомендации плана (указание владельца выше): звенья хоста
(firewall, portproxy, задачи) от образа не зависят, и откат рабочего образа
из-за настройки хоста ничего не чинит. Прагматик совета согласен.

**Совет по плану, круг 1.** Код 0, блокеров нет. Приняты все замечания:
тег нового коммита задаётся до `pull` и `migrate` (инженер); состояние
отката хранится на диске и переживает обрыв процесса (скептик); постоянная
сквозная проверка в ci-heavy убрана — один живой прогон на стенде с записью
сюда (прагматик); один Windows-тест обёртки вместо двух; сборка стадии
`migrations` — первым шагом реализации.

**Срез image: скан образа — только наше содержимое (расхождение с
контрактом).** Скан всех слоёв с `.gitleaks.toml` проекта дал 40 находок в
api и 2 в migrate — все в файлах базовых образов (`/var/lib/dpkg`,
`/etc/ssl/openssl.cnf`, `deps.json` .NET, `perl-base`), в `/app` и
`/migrations` — ни одной. `deploy/build-images.sh` сканирует `/app`,
`/migrations` и JSON конфига образа: секрет может прийти только из нашего
контекста сборки, а базовые образы — закреплённые upstream. Новая точка
`COPY` в финальной стадии добавляется в список путей скана той же правкой —
напоминание в Dockerfile и в шапке сценария.

**Срез image: `--no-transactions` у `migrations script`.** Скрипт EF
`--idempotent` несёт свои `START TRANSACTION`/`COMMIT` внутри
`psql --single-transaction`: при двух и более миграциях всё после первого
внутреннего `COMMIT` шло бы вне транзакции. С флагом атомарность держит
`--single-transaction`.

**Срез envfile: решения там, где контракт молчит.** `set` отклоняет
значение с CR/LF (код 2); `set` и `unset` при дублях ключа правят все его
строки — иначе `dotenv_value` («последняя побеждает») читал бы старое; `get`
ключа вне белого списка — код 2 без вывода; `sync --dry-run` секрет не
генерирует; разметка `# env-sync:` действует, только если стоит строкой прямо
над ключом. Ключ owner, который в `.env` есть, но пуст, строки «заполните» не
получает — критерий говорит о новом ключе. Раскомментированный у владельца
`COMPOSE_PROFILES` попадает в «лишние»: по задаче лишние только
перечисляются, это не ошибка.

## Отвергнуто

- Исключения базовых файлов в `.gitleaks.toml` — ослабление правил поиска
  секретов (группа `former_protected`), и на PR правила берутся с базы.
- Различать свои и базовые слои по `diff_ids` — у сжатых слоёв OCI дайджесты
  не совпадают, много подкоманд docker для подделок, осуществимость не
  проверена.
- Отдельный конфиг gitleaks для образов только со встроенными правилами —
  правила проекта (имена хостов, IP, пароль БД) в образе не проверялись бы.

- Откат образа по красному `engine-setup.ps1 -Check` (буквально п. 3.6–3.7
  issue) — откатывает рабочий образ из-за настройки хоста.
- Сквозной `deploy/update.e2e.sh` в ci-heavy — постоянная тяжёлая проверка
  сверх критерия; критерий требует прогона, он делается на стенде.
- Разбиение на три задачи (GHCR, `update.ps1`, WSL-настройки) — владелец
  выбрал один PR.
