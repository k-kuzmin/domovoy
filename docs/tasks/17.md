## Решения

**Триаж (2026-11-11).** Не готова из-за одного вопроса — пункт критерия
«срабатывание лимита видно в метриках»: метрик в `main` нет, экспорт в
стандартном формате вводит открытая #27 (stage/2). Остальные пункты
проверяемы: серия запросов сверх порога в тесте, формат 429 уже есть
(`ApiErrorResults.RateLimited`), логи с `request_id` есть после #18.
Существующий лимитер привязки устройства (`PairingRateLimit`) стоит на
встроенном `Microsoft.AspNetCore.RateLimiting` — нового пакета не нужно,
общий лимит расширяет этот механизм, а не дублирует его. #27 триаж
пропустил, она добавлена оркестратором.

**Метрика срабатывания (владелец, 2026-11-11).** Счётчик без экспорта:
встроенный `System.Diagnostics.Metrics`, проверка тестом через
`MeterListener`; наружу его выведет #27. Без новых пакетов и без анонимного
эндпоинта.

**«Все эндпоинты» — буквально, включая `/health`.** Исключение health из
лимита меняет критерий; спросить не у кого сверх уже заданного вопроса,
принято буквальное прочтение — порог общего лимита задаётся конфигурацией.

**Совет по плану, круг 1 (2026-11-11).** `council.sh` — код 0, блокеров
нет; страж и инженер — `no_objections`, скептик и прагматик —
`another_round`. Два major: сканер исчерпывает анонимный раздел и через
него — `/health` в `update.sh` и привязку (скептик); размер выше порога
(прагматик). По размеру: запись 0035 остаётся отдельной — принятое 0033 про
`/auth/device` задним числом не переписывается, — но идёт в срезе limiter;
валидатор — в файле опций. Имена метрики сверены оркестратором по
`Microsoft.AspNetCore.RateLimiting.dll` 8.0.33: счётчик
`aspnetcore.rate_limiting.requests`, теги
`aspnetcore.rate_limiting.result` и `aspnetcore.rate_limiting.policy` —
снимает `unable_to_verify` скептика.

**Исправление плана по кругу 1.** Анонимный раздел — на каждую конечную
точку (`anonymous:<имя>`); 404 без токена получают 401 до лимитера
(`FallbackPolicy`, `Program.cs:72`) — подтверждает тест. Против отката
обновления надёжной меры без выбора нет — в карточке развилка A/B/C,
триггер «позвать человека». `curl` в образе api есть (`Dockerfile:68`) —
сверено оркестратором для варианта A.

**Развилка и план (владелец, 2026-11-11).** Вариант A — `update.sh`
проверяет тело `/health` изнутри контейнера (`compose exec api curl`), с
хоста — только что порт отвечает. План принят как есть, в реализацию. План
после ответа не менялся (A в нём уже был) — второй круг совета не нужен.

**Срезы limiter и tests перенесены (2026-11-11).** Файлы срезов совпали с
`files`. Тесты среза tests на базе красные по существу — 8 из 8 (нет 429,
нет отказа старта, нет отказных измерений). Расхождения срезов с планом:
опции через `BindConfiguration` внутри `AddApiRateLimits()`; ключ анонимного
раздела — `IEndpointNameMetadata`, без него `DisplayName`; коллекция
`RateLimitingTests` непараллельная (`OutboundHttpLoggingSerialGroup`) —
тест лога читает общий логгер процесса; в тесте лога добавлены проверки
`RateLimitPartition`/`RateLimitEndpoint`.

**Двойное списание общего предела (оркестратор).** После склейки красный
один тест — метрика: третий `/voice` при общем 3 и `llm` 2 отклонял общий
лимитер. Причина — middleware ASP.NET Core 8 после отказа политики
повторяет захват путём ожидания, фиксированное окно не возвращает
разрешений: отказ `llm` списывает два общих разрешения. Это поведение
фреймворка, не дефект реализации; в тесте общий предел поднят до 5 с
запасом (утверждения те же), цена записана в 0035, «Цена».

## Отвергнуто

- Экспорт метрик (`/metrics` или OpenTelemetry) в этой задаче — новый
  анонимный эндпоинт или новая зависимость; это предмет #27.
- Отложить #17 до #27 — #27 крупная (6–12 ч, дробится), лимиты нужны раньше.

## Шаги

- Воспроизведение пропущено — задача не баг.
- Совет по плану — по маршруту high (все четыре роли). Признаки: контракт
  API (429 на всех маршрутах), общий механизм (глобальный лимитер на весь
  конвейер), глобальный переключатель, правка обвязки (`docs/decisions/`),
  новая функциональность.
- Метрика: план берёт встроенный счётчик фреймворка
  `aspnetcore.rate_limiting.requests` вместо своего — тот же
  `System.Diagnostics.Metrics` без экспорта, что выбрал владелец; показать
  владельцу вместе с планом.
- Срез deploy добавил второй сценарий сверх плана —
  `update_rolls_back_on_bad_health_body_inside_container`: без него ничто не
  доказывало, что тело `/health` проверяется изнутри контейнера.
- Совет по диффу — признаки плана переносятся на дифф (контракт API, общий
  механизм, переключатель, правка обвязки, новая функциональность); состав
  high — все четыре роли.
