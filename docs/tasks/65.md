## Границы

Входит:

- перенос правил из промптов `.github/workflows/agent-*.yml` в `docs/rules/`
  с заменой текста на ссылки и указателем из `.claude/CLAUDE.md`;
- пункт ревью корректности: сверка сделанного с утверждённым планом;
- момент создания чернового PR — по готовности реализации, а не по первому
  зелёному прогону; половина «ветка пушится рано и часто» не двигается;
- возвратное плечо цикла: перезапуск ревью после починки, потолок 2 круга,
  метки `review/1`, `review/2`, на третьем круге `agent/needs-human`.

Не входит:

- механическая проверка, что промпты не разъехались с `docs/rules/`;
- разбивка `CLAUDE.md` на тонкое ядро и темы — отложено владельцем в #63;
- `labeled` у `ci-fast.yml`, дубли gitleaks, кэш NuGet для CodeQL — найдено
  при разборе пайплайна в #63, к правилам отношения не имеет;
- прямое плечо цикла «вердикт → починка» — зависит от ответа владельца.

## Вопросы и ответы

| Вопрос | Ответ | Кто ответил |
|---|---|---|
| Счётчик кругов ревью — общий с `fix/1..3` или отдельный | Отдельный: `review/1`, `review/2`. Поводы разные — падение CI и замечание ревьюера не одно и то же | владелец (комментарий в #65) |
| Момент создания чернового PR | Порядок прежний (PR → ревью → исправление), но черновой PR открывается по готовности реализации. «Ветка пушится» остаётся как есть — это защита от потери, а не видимость | владелец (комментарий в #65) |
| Прямое плечо цикла «вердикт `changes_requested` → `agent-fix`» — входит в #65 | Задан в плане, ответа пока нет. Все четыре пункта задачи от него не зависели и сделаны | — |
| Пять файлов правил или шесть | Спросить некому. Допущение: шесть — ревью разнесено на корректность и безопасность, потому что два job разделены намеренно. Один файл на два job вернул бы ревьюера, который заканчивает список после третьего пункта | — |

## Решения

**Правила — слой поверх `CLAUDE.md`, а не самостоятельный документ.** Запреты
(подавление предупреждений, отключение тестов, правка пайплайна) остаются
каноническими в разделе «Запрещённые способы „починить“ сборку»,
`docs/rules/implement.md` и `fix.md` на него ссылаются. Отвергнуто: сделать
файлы правил самодостаточными — вместо двух копий стало бы три, ровно то,
против чего задача.

**Возвратное плечо замыкается комментарием `/review`, а не триггером
`synchronize`.** Отвергнуто добавление `synchronize` в `on:` — формулировка
самой задачи, но оно срабатывает на каждый пуш в PR, включая пуши по ходу
реализации, и без дополнительного условия оплачивало бы два ревью на каждый
коммит. `agent-fix`, запушив починку по замечаниям, сам пишет комментарий
`/review` через AGENT_TOKEN: событие от PAT запускает workflow, вход
существующий, и срабатывает он только там, где починка была вызвана ревью.

**Счётчик кругов — отдельный job до вызова модели.** Дублировать шаг счёта
внутри `correctness` и `security` нельзя: они гонялись бы за право поставить
`review/N`, и оба сожгли бы вызов модели на стоп-круге. Job `round` считает
круг по меткам и отдаёт `stop`, два ревью встают на него через `needs:`. Та же
дисциплина, что у `fix/N` в `agent-fix.yml`: метка ставится до работы, потому
что считает круги, а не успехи.

## Найдено при разборе

**Прямое плечо цикла ревью, похоже, недостижимо.** `agent-review.yml` печатает
вердикт через `gh pr comment` и никогда не делает
`gh pr review --request-changes`. А `agent-fix.yml` ждёт события
`pull_request_review` с `state == changes_requested` и
`author_association == 'OWNER'`. Ветку и PR создаёт `agent-implement` через
AGENT_TOKEN, то есть автор PR — владелец, а GitHub запрещает запрашивать
изменения в собственном PR. Если это так, замыкание возвратного плеча даёт
цикл, у которого не запускается прямое. Ограничение проверяется вызовом API на
живом PR этой задачи; рамки — за владельцем.

## Проверено

- **Прямое плечо цикла действительно недостижимо.** Проверено вызовом API на
  живом PR #66: `gh api repos/…/pulls/66/reviews -f event=REQUEST_CHANGES`
  отвечает `422 Unprocessable Entity`, «Review Can not request changes on your
  own pull request». Догадка из разбора стала фактом: пока автор PR — владелец
  (а ветку пушит `agent-implement` его же токеном), путь
  `pull_request_review` в `agent-fix` запускается только человеком вручную.
- YAML всех девяти процессов разбирается — `yaml.safe_load`, 9 из 9.
- `scripts/guard.test.sh` — 20 сценариев из 20, включая новый на `docs/rules/`.
- Логика счёта кругов на наборах меток: пусто → круг 1; `review/1` → 2;
  `review/1`+`review/2` → стоп. `fix/1..3` на счёт не влияют; `review/10` не
  даёт ложного срабатывания (`grep -qx`).
- Ни один пункт прежних промптов ревью не потерялся: из 16 заголовков в старой
  версии `agent-review.yml` в `docs/rules/` нашлись все 15 содержательных
  (шестнадцатый — `$verdict` из shell-эха).
- Поиск по `agent-*.yml` после переноса: содержательных критериев в промптах не
  осталось, совпадения — только имена полей схемы (`blocker_count`), ссылки на
  разделы `CLAUDE.md` и `if-no-files-found: ignore`.
- Метки `review/1`, `review/2` заведены `scripts/bootstrap.sh` (16 меток,
  скрипт идемпотентен), проверено `gh label list`.
- `gitleaks git --staged` — чисто на каждом из пяти коммитов.
- Гейт целостности на PR #66 — зелёный с первого прогона: метка
  `agent/allow-protected` поставлена **при создании** PR (`gh pr create
  --label`), а не после. Ровно та грабля, на которую наступили в #63.
- Локально `dotnet build` / `dotnet test` не запускались: прикладной код не
  тронут, дифф целиком в правилах, промптах и обвязке. Сборку и тесты прогнал
  CI.

## Осталось

**Прямое плечо цикла не замкнуто** — вердикт `changes_requested` не запускает
починку. Ограничение GitHub подтверждено (см. «Проверено»), поэтому настоящее
плечо требует отдельного входа: комментарий `/fix` у `agent-fix` либо метка.
Рамки — за владельцем; вопрос задан в issue.

**Правки не проверены на живом прогоне** — цикл выключен
(`vars.AGENT_LOOP_ENABLED` не задана), настоящего ревью и настоящей починки, на
которых сработали бы job `round` и шаг «Ревью заново», взять негде. То же
ограничение, что в #63.

**Не проверено, хватает ли `pull-requests: write` для метки на PR.** Job
`round` ставит `review/N` тем же способом, которым `agent-fix` ставит `fix/N`,
то есть повторяет существующий и тоже ни разу не проверенный путь. Если
понадобится `issues: write` — узнается на первом живом прогоне.

**Механической проверки, что промпты не разъехались с `docs/rules/`, нет.**
Промпт может продолжать ссылаться на файл, из которого правило удалили. Та же
природа, что у наблюдения про `ast-index` в #63: правило есть, механики нет.
