## Решения

**Триаж (2026-10-12).** Вердикт `ready: false`, два вопроса. Ссылки на ТЗ
(AR-5, 5.1.3) существуют, противоречия с правилами проекта нет.

- Место бэкапа. Владелец (2026-10-12): **внешний диск / USB**, подключённый к
  хосту. Новых зависимостей нет; путь задаётся конфигурацией, в README —
  только плейсхолдер.
- Среда проверки восстановления. Владелец (2026-10-12): **тот же хост, пустые
  тома** — отдельный проект compose с чистыми томами, восстановление из
  последнего бэкапа, проверка: HA видит устройства, Backend видит свои данные.
- Хост — Windows 11 (ответ владельца по #6); расписание — средствами хоста.

**Совет по плану, круг 1 (2026-10-12).** Страж и инженер — `no_objections`,
скептик — `another_round`; `council.sh` — код 0, блокеров нет, принято 7
замечаний (2 major скептика, 5 nit), все внесены в план шагом плана.

**Опыт к major скептика «HA в internal-сети не даст состояний» (2026-10-12).**
Агенту запуск копии тома HA закрыт классификатором прав; сценарий прочитан
оркестратором и запущен владельцем через `!`. Копия тома HA (рабочий том
только на чтение, без базы рекордера) в `--internal`-сети, HA 2026.10.1:
реестр — 73 записи, не отключённых — 59; в `/api/states` присутствуют
**59 из 59**, из них `unavailable` — 45; недостачи по платформам нет.
Правило «N из N» остаётся без ослабления, замечание снято.

**Развилка карточки (2026-10-12).** Владелец: проверка восстановления —
**в изолированной сети, без простоя** рабочего стека; «HA видит устройства» —
все не отключённые сущности реестра из бэкапа есть в `/api/states`.

**Реализация (2026-10-12), шаг `step-implement`.** 10 коммитов, 6843697..677d974.
Расхождения с планом (по отчёту шага, сверяются ревью):
- архив тома HA — `tarfile` python образа HA, а не busybox `tar`: в busybox
  1.37 `-C` одноразовый, не склеить `/config` и онлайн-копию рекордера;
- онлайн-копия — для всех баз sqlite тома (тот же класс: `zigbee.db` в WAL),
  `home-assistant.log*` исключён;
- том HA распаковывается через временный контейнер и `docker cp`;
- порты в `--check` снимаются `ports: !reset []`;
- новый `ops/backup/table-counts.sql` — один источник подсчёта строк;
- `restore.sh`: `--keep`, `RESTORE_CHECK_PROJECT`; `compare --expect N`;
- `/health` засчитывается при любом статусе: в `internal`-сети недоступный
  LLM даёт 503 — данные Backend подтверждает сверка таблиц с манифестом;
- `.partial` удаляется при провале бэкапа; `restore.sh` вызывает `up --build`;
- в тесте K берётся из живого реестра (встроенная интеграция `backup` HA
  добавляет 5 сущностей с задержкой), K ≥ 3;
- порт API на хосте в сценариях не используется (всё через `exec`).
TDD: красный прогон показан для модуля и масок `.gitignore`; у `backup.sh` и
`restore.sh` отдельного красного прогона не было.

**Ревью диффа и совет по диффу, круг 1 (2026-10-12).** Совет: страж и
прагматик — `no_objections`, скептик и инженер — `another_round`;
`council.sh` — код 0. Ревью: безопасность и корректность —
`changes_requested`. Принятые замечания (A–J) исправлены шагом `step-fix`,
коммиты 6bb06f4..1f8478b:
- числа таблиц манифеста — из временной базы, восстановленной из самого дампа
  (вариант Б), а не отдельным `psql` по живой базе; в `restore.sh` сверка
  таблиц — сразу после `pg_restore`, до старта api; тест с писателем в
  `domovoy_churn` параллельно с бэкапом;
- число реестра HA — из тех же байтов, что легли в архив;
- сверка состояний — с реестром из архива бэкапа (`/tmp/registry.backup.json`),
  а не с реестром, который HA переписал при старте;
- `restore.sh --project` отказывает, если на хосте работает HA другого
  проекта; README — рядом с рабочим стеком только `--check`;
- токен HA — заголовком через stdin `curl -H @-`; `umask 077`; состав
  замера строкой рядом; `integrity_check` всех баз sqlite тома; текст отказа
  без реестра в тесте; исчезнувший при архивации обычный файл пропускается.
Прагматик (nit, defer части `backup.test.sh`) — не принято: сценарии теста
закрывают пункты A2, A2-backend-data и A3 контракта.

Блокер корректности «A1, A2, A2-backend-data, A4 не пройдены» — не дефект
кода: закрывается работой CI `backup` на PR и живыми прогонами владельца.

**Гонка postgres — исправлена в первопричине (2026-10-12).** Шаг починки
поймал в полном прогоне `pg_restore: … the database system is shutting down`
после `postgres Healthy`. Причина — healthcheck postgres в
`docker-compose.yml`: `pg_isready` без `-h` ходит через сокет и зеленеет на
временном сервере инициализации `docker-entrypoint.sh`
(`listen_addresses=''`). Опыт, плотный опрос в контейнере `postgres:16-alpine`
при первой инициализации: сокет `ok`/TCP `no` — 29 замеров, затем оба `no`
(остановка временного сервера), затем оба `ok`. Healthcheck переведён на
`pg_isready -h 127.0.0.1` (75b21e2). Тот же healthcheck гейтит
`depends_on: service_healthy` у api — гонка снята и для него. Правка
`docker-compose.yml` в плане не заявлена — расхождение, записано здесь.
