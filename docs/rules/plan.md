# План реализации

План обсуждается до того, как написана первая строка кода. Это не формальность
инструмента: несогласие с подходом стоит одного комментария, а не выброшенного
PR.

На этом шаге код не пишется.

Правила проекта — `.claude/CLAUDE.md`, читать из репозитория. Обязательны
разделы «Архитектура», «Границы работы агента», «Правила синхронизации»,
«Definition of Done».

## Семь разделов

1. **Как устроено сейчас.** Что уже есть в коде по этой теме, с путями к
   файлам и именами типов. Без этого раздела план — догадка: он показывает,
   что существующее прочитано.
2. **Подход.** Одно решение, а не перечень вариантов. Если вариантов было
   несколько — назвать отвергнутые одной строкой и почему.
3. **Файлы.** Что создаётся, что меняется, по каждому — зачем. Отдельно
   отметить файлы из раздела «Границы работы агента»: их правка требует метки
   `agent/allow-protected`, изменение контракта API — `agent/allow-contract`.
   Гейт целостности `scripts/guard.sh` завернёт PR без нужной метки.

   **Правку конфигурации прав шага плану поручать нельзя** — ни списка команд
   в хуке `PreToolUse`, ни поля `tools`, ни определения
   `.claude/agents/step-*.md`. Такую правку делает оркестратор: метка снимает
   гейт в CI, но согласие человека внутрь субагента не передаёт. Обоснование —
   запись [0018](../decisions/0018-local-orchestrator-and-step-subagents.md),
   раздел «Кто правит конфигурацию прав шага». План, поручивший это шагу
   реализации, упрётся в отказ на середине работы.
4. **Тесты.** Какие тесты появятся и какое поведение каждый проверяет. Тест,
   проходящий при сломанной реализации, хуже отсутствующего — формулировать
   проверяемое поведение, а не «покрытие класса».
5. **Контракт приёмки.** Строка на каждый пункт критерия готовности из issue,
   таблицей: пункт → способ проверки → что считается доказательством. Апрув
   плана и подтверждённый результат — разные утверждения, и второе без этого
   раздела не проверяет никто.

   Способ проверки — команда с ожидаемым результатом, запрос или наблюдение.
   Доказательство — то, что можно предъявить: вывод команды, число, цитата
   `файл:строка`. Способа нет — в ячейке стоит значение `непроверяем` и
   причина, почему его нет. **Пустая ячейка не допускается**: она не отличает
   «способа нет, и вот почему» от «забыли заполнить», а различение этих двух и
   есть смысл раздела.

   Раздел обязателен в каждом плане — исключения для задач, где не появляется
   ни строки кода, нет. Для них способом проверки становится прогон скрипта
   обвязки с ожидаемым кодом возврата, точная цитата `файл:строка` или
   отсутствие копий в выводе поиска. Условие «обязателен, если затрагивается
   исполняемый код» отвергнуто: границу исполняемого кода проводит читающий, а
   это ровно то усмотрение, которое контракт и убирает.

   Проходит контракт по пунктам ревью корректности —
   [`review-correctness.md`](review-correctness.md), пункт 1. Пункт со
   значением `непроверяем` работу не отменяет, но обязывает ревью назвать его
   вслух.
6. **Риски.** Что может пойти не так: ломающее изменение контракта, миграция
   БД, направление зависимостей между проектами, расхождение системного
   промпта и набора инструментов.
7. **Что не входит.** Границы задачи. Замеченное попутно — новая issue, а не
   незапланированная правка.

## Когда план составить нельзя

Противоречие в требованиях, отсутствие нужного решения в `docs/decisions/`,
критерий приёмки, невыполнимый в заданных границах, — повод остановиться и
объяснить, чего не хватает.

Остановка с объяснением — нормальный результат. Догадка в плане — нет: она
закрепится в коде, и через месяц её будет не отличить от решения.

## Что происходит с планом дальше

План уходит комментарием в issue и ждёт апрува человека — метки
`plan/approved`. Комментарий «одобряю» метку не заменяет.

Согласованный план — обязательство, а не набросок. Расхождение с ним по ходу
реализации описывается в PR отдельным абзацем, и ревью это проверяет
(`review-correctness.md`).
