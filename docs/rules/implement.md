# Реализация

План согласован по минимуму маршрута — можно писать код. План при этом
обязательство, а не набросок.

Правила проекта — `.claude/CLAUDE.md`, читать из репозитория, а не по памяти.
Обязательны разделы «Архитектура», «Запрещённые способы «починить» сборку»,
«Правила синхронизации», «Git», «Журнал задачи», «Definition of Done».

## Порядок работы

1. **Ветка и журнал уже есть** — их завёл оркестратор до плана. Работа идёт
   в ветке задачи. Журнал и пуш — у оркестратора (`.claude/CLAUDE.md`,
   «Журнал задачи»): реализует субагент — он коммитит и возвращает сделанное
   в ответе; реализует сам оркестратор — он же обновляет журнал на каждом
   коммите. Исключение — срез: он работает на временной ветке, раздел
   «Склейка срезов».
2. **Сначала тест, падающий по существу.** Написать тест на требуемое
   поведение, убедиться, что он падает по той причине, ради которой написан,
   и только потом писать код. Тест, который проходит при сломанной
   реализации, хуже отсутствующего.

   Для бага: фикс, потом убедиться, что воспроизведение больше не падает. Если
   воспроизведение уже было тестом, оно и остаётся регрессионным.
3. **Проверять по ходу** — раздел «Проверки по ходу». Красное чинится сразу,
   до следующего шага.
4. **Коммитить по ходу.** Conventional Commits, один коммит — одно логическое
   изменение, без подписей инструмента (`.claude/CLAUDE.md`, «Git»). Ветку
   пушит оркестратор — после первого зелёного прогона и дальше часто.
5. **Синхронизация.** Обновить то, что перечислено в таблице «Правила
   синхронизации» в `.claude/CLAUDE.md`, — по тому, что реально изменилось.
6. **Живая проверка** — раздел «Живая проверка».
7. **Расхождение с планом** — что изменилось и почему — попадает в журнал в
   момент решения (у субагента — отдельным абзацем ответа, оркестратор
   переносит его в журнал) и уходит в PR отдельным абзацем. Ревью диффа идёт
   до PR и сверяет расхождения по журналу: не записанное там — необъяснённое.
8. **Последним действием** — строка `Следующий шаг` в шапке журнала, её
   пишет оркестратор. Она адресована тому, кто продолжит работу с чистого
   листа.

PR этот этап не открывает: он открывается после ревью диффа
(`.claude/CLAUDE.md`, «Рекомендованный порядок»).

## Склейка срезов

Действует, когда в `fork_card.slices` плана больше одного среза. Что такое
срез и его поля — [`plan.md`](plan.md), «Карточка развилки»; здесь — как
срезы исполняются и собираются в ветку задачи.

**Запуск — оркестратор.**

1. План и журнал коммитятся и пушатся до запуска срезов: worktree создаётся
   от закоммиченного состояния, а worktree агента может создаться и от
   `origin/<ветка по умолчанию>`, а не от ветки задачи.
2. Каждый срез исполняет отдельный `step-implement` с
   `isolation: "worktree"`. Срезы без `after` запускаются
   одним сообщением.
3. Срез с `after` запускается после переноса своих зависимостей — от
   коммита ветки задачи, в который они уже перенесены.
4. Промпт среза называет его файлы и контракт, базовый коммит (SHA и
   `git checkout -B slice/<N>-<срез> <SHA>`) и временную ветку. Абзац
   «Ветка» определения `.claude/agents/step-implement.md` требует
   остановиться вне `feat/<N>-…`; промпт оговаривает это исключение явно.

**Внутри среза.**

- В свежем worktree с .NET первым шагом идёт `dotnet restore`: это и есть
  повод из «Проверок по ходу» — без восстановленных пакетов
  `dotnet build --no-restore` не соберётся.
- Срез коммитит в свою временную ветку, не пушит, журнал и план не трогает.
- Git — простыми командами по одной: в сессии, изолированной в worktree,
  составные команды с git отбиваются. Сценарии обвязки запускаются
  скриптом целиком, а не циклом в команде.
- Если `core.hooksPath` задан абсолютным путём, коммит в worktree
  запускает хуки основной копии — её текущей ветки, а не ветки среза.

**Перенос — оркестратор.**

1. До переноса `git diff --name-only <база>..<ветка среза>` сверяется с
   `files` среза. Срез вышел за свои файлы — работа возвращается срезу, а не
   правится руками.
2. Коммиты переносятся в ветку задачи `git cherry-pick` в порядке `after`.
3. После переноса на ветке задачи — полный набор тестов и сверка стыков по
   `contract`: имена, аргументы и формат данных, обещанные срезом, совпадают
   с тем, что читают соседи. `cherry-pick` хуки коммита не запускает,
   поэтому секреты проверяются по диапазону:
   `gitleaks git --redact --no-banner --log-opts="origin/main..HEAD"`.
4. Ветка задачи одна; ветки срезов и их worktree временные и удаляются
   после переноса. Журнал и план правит только оркестратор — сделанное и
   расхождения срезов он переносит туда из их ответов.

## Проверки по ходу

После каждого осмысленного шага:

    dotnet build --no-restore -c Release
    dotnet test --no-build -c Release

Ещё две команды — не на каждом шаге, а по поводу:

    dotnet restore
    dotnet format --verify-no-changes --no-restore

`restore` — когда менялись `*.csproj` или `Directory.Packages.props`: пока
файлы проекта не изменились, другого результата он не даст. Проверка стиля —
перед коммитом, а не после каждой правки. Каждый лишний прогон — лишний ход, а
ход пересылает весь накопленный контекст. **Перед пушем прогоняются все
четыре.**

## Когда пишется регрессионный тест

| Правка | Тест |
|---|---|
| баг в поведении кода | обязателен: воспроизведение, ставшее тестом, — красное до фикса, зелёное после |
| новое наблюдаемое поведение | обязателен на каждое поведение из контракта приёмки плана |
| правка общего механизма или переключателя | обязателен на сценарий вне задачи, который правка могла задеть (из `ripple` карточки) |
| рефакторинг без изменения поведения | новый не нужен: существующие тесты проходят без правки утверждений |
| сценарий обвязки в `scripts/` | сценарий в `scripts/<имя>.test.sh` на изменённое поведение |
| конфигурация, `.example`, документация | не нужен: проверка — способом из контракта приёмки |
| правка, которую тест не различит (текст сообщения, стиль) | не нужен; так и записывается в журнал |

Ослабить или удалить существующий тест, чтобы правка прошла, нельзя —
`.claude/CLAUDE.md`, «Запрещённые способы «починить» сборку».

## Живая проверка

Зелёные тесты значат «собралось и юниты проходят», а не «работает». Если есть
что запускать, результат запускается: `dotnet run --project src/Domovoy.Api`
или `docker compose up -d --build --wait` и запрос к затронутому эндпоинту, `curl -s
http://localhost:18080/health` — для правки, задевающей старт. В журнал, в «что
проверено», идёт команда и её фактический вывод, а не пересказ.

Пропуск — только по одной из двух причин, и причина пишется в журнал:

- код недостижим из запускаемого приложения (заглушка этапа, нет точки
  входа);
- у правки нет наблюдаемого следствия (документация, переименование без
  изменения поведения).

## Миграции

Правила expand/contract — `.claude/CLAUDE.md`, «Миграции БД». Сверх них —
порядок версий, который механически не проверяет никто:

- метка версии новой миграции выше последней миграции на `origin/main`:
  `git -c core.quotePath=false ls-tree --name-only origin/main src/Domovoy.Data/Migrations/`;
- миграция, уже попавшая в `main`, не переименовывается и не пересоздаётся;
- в `main` появилась миграция новее, пока ветка жила, — своя пересоздаётся
  поверх (`dotnet ef migrations add` после обновления ветки), а не правится
  метка в имени файла: иначе снимок модели разойдётся с порядком применения.

Применение миграции к базе (`dotnet ef database update`) — команда человека.

## Чего делать нельзя

Список запретов — раздел «Запрещённые способы «починить» сборку» в
`.claude/CLAUDE.md`. Сверх него, на этом этапе:

- **выходить за рамки задачи** — граница попутного в разделе «Поведение при
  неопределённости», адрес находок — в разделе «Находки» `.claude/CLAUDE.md`;
- **добавлять зависимость без обоснования** — любая новая библиотека требует
  обоснования в комментарии к issue до установки; новая зависимость —
  триггер «позвать человека».

Задача не сходится по существу — остановиться и сказать об этом человеку.
Остановка с объяснением — нормальный результат. Зелёная сборка, добытая
подавлением, — нет.
